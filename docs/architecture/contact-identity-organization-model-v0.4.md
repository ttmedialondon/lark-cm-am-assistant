# 人员身份、组织与负责人模型（当前策略）

## 目标

把 Lark 中的“一个人”拆成独立、可追溯的四类事实：

1. **人员身份**：稳定 Lark `open_id` 聚合出的联系人；
2. **所属组织**：该联系人与组织的可验证关系；
3. **业务类别**：此人对 TT Media London 的业务角色；
4. **负责人**：已确认达人由哪位已接入 CM/AM 跟进。

四类事实不能相互替代。例如，某人属于 MCN 租户不代表其一定是 MCN 的负责人；某人被归为达人也不自动分配 CM/AM。

## 人员类别

| 代码 | 管理台名称 | 含义 |
| --- | --- | --- |
| `creator` | 达人 / 内容创作者 | 本人是合作的创作者、KOL、主播或内容生产者。 |
| `partner_contact` | 合作机构对接人 | MCN、经纪公司、代理、服务商等机构的代表或沟通窗口；不推断其具体职级。 |
| `internal_colleague` | TT Media London 同事 | 由内部 Lark 租户事实确定，不由模型猜测。 |
| `merchant_contact` | 商家 / 品牌方对接人 | 品牌、店铺、卖方或其业务代表。 |
| `platform_contact` | 字节系平台官方对接人 | ByteDance、TikTok 等平台侧正式业务联系人。 |
| `other_external_contact` | 其他已确认外部联系人 | 有充分业务事实，但不属于以上类别的外部人员。 |
| `NULL` | 待识别 | 尚未获得足够可靠证据；绝不等同于“其他人员”。 |

`insufficient` 仅是模型的“信息不足”输出，不会写成业务类别。

## 数据模型

### 人员与稳定身份

- `contacts`：当前以一个稳定 Lark `open_id` 为单位的联系人记录；
- `lark_identities`：该记录对应的稳定 Lark 身份（`open_id`、`tenant_key`、租户属性）；
- `contact_roles`：已确认的业务角色。其中恰好一个显示为主类别，其他已确认角色显示为“辅助”标签；切换主类别不会抹掉仍成立的辅助事实。内部同事由 Lark 内部租户事实重建。

当前不会仅凭相同显示名合并不同 Lark 账号。跨账号合并只能在 CRM 精确 ID、已验证邮箱/电话或管理员人工确认后再加入；否则容易把同名外部人员误合并。

### 组织

- `organizations`：规范化组织名称和组织类型；
- `organization_tenants`：`tenant_key → organization` 的已验证映射；
- `contact_organization_links`：`contact → organization` 的关系、来源、置信度与状态。

组织来源按可信度使用：Lark Trust Party、CRM、管理员人工确认。组织资料独立维护，当前不输入联系人角色模型，也不阻塞角色识别。

### 负责人

- `contact_assignments`：达人当前唯一负责人、来源、置信度、生效和结束时间；
- 负责人不是人员类别，也不是组织属性。交接始终人工完成。

## 自动识别流程

```text
Lark 消息 / 成员 / 稳定身份
             │
             ├── 内部租户 → 直接确认 TT Media London 同事
             │
             └── 外部联系人
                    │
                    └── 当前授权范围内的消息与互动关系
                           → Luna 角色分类 → 建议或确认
```

只要外部联系人有一条仍在当前授权范围内的消息正文，即可进入角色识别队列。组织仍可由关联组织、CRM 或管理员独立维护；确认整租户归属时才可建立租户映射，但它不改变本轮角色判断。

### 证据包

每次只处理一个联系人，并传入：

- 一条命中消息、同会话前后各最多 6 条、该联系人近期最多 4 条发言；
- 会话类型、外部群标记、P2P 对端、回复链与 @ 关系；
- 每条消息的匿名证据编号 `M1…`，而不是让模型自由引用内容；`speaker_tenant=internal` 只表示我方公司一侧。

不会输入组织名称、组织类型、`tenant_key → 组织`映射或组织候选。群名只能是弱背景；聊天正文被明确标为不可信输入，不能改变模型指令。请求使用 OpenAI Responses API 的无状态模式 `store: false`。

### 模型输出与决策

模型只能返回 1–3 个类别建议、置信度、依据类型和 `M` 证据编号。

服务端验证所有证据编号真实存在且仍在授权范围内，再决定：

| 条件 | 结果 |
| --- | --- |
| 唯一业务类别、≥90%、且为授权 CM/AM 的 P2P、与内部同事的回复/@ 互动或本人自述 | 自动确认主类别。 |
| 70%–89%，或存在多个业务类别建议 | 留在该联系人详情页供人工确认。 |
| <70% 或 `insufficient` | 不建候选、不写类别。 |

已确认类别的联系人不再进入自动身份识别队列。组织关系只能由关联组织、CRM 或管理员人工确认，整租户映射必须额外勾选。

## 管理台流程

### 人员目录

- 按主类别、组织状态和组织名称筛选；
- 显示组织、会话数、发送消息数、最近活动和租户属性；
- “Lark 身份”只表示内部/外部/未返回租户，不冒充真实业务类别。

### 联系人详情

1. 展示稳定 Lark 身份、组织关系和相关会话统计；
2. 展示该联系人的 AI 状态、建议与引用证据；
3. 人工确认类别或独立维护组织；
4. 只有已确认达人才展示负责人和人工交接入口。

所有消息正文仍只在审计过的 AI 证据/消息内容页面显示；目录与联系人详情默认仅显示元数据和统计。

## Lark 组织资料来源

首选的 Lark Trust Party 范围为：

- `trust_party:collaboration_rule:read`
- `trust_party:collaboration.tenant:readonly`

它用于同步关联组织及 `tenant_key → organization` 映射。内部员工的部门、职务和在职状态应通过通讯录 API 单独同步，不能拿内部通讯录接口查询外部人员。

若当前 Lark 应用尚未获得 Trust Party 能力，系统仍保持消息同步与角色识别。管理员可以在联系人详情页录入经核验的单人组织关系；只有明确知道整个租户都属于该机构时，才勾选租户映射。
