# 达人自动识别流程

版本：1.0。更新：2026-10-14。

目标是把名单导入、新加入联系人和已确认达人的账号补配，整理为同一套证据规则。身份、handle、负责人独立成立；AI 理解业务证据，后端控制权限、任务和入库。

本版已建立后台可编辑的六份处理手册，固定下一步实现口径。手册尚未接入达人执行器，发布文档不代表新联系人自动识别已经上线。

## 1. 当前系统

| 场景 | 当前实际行为 |
| --- | --- |
| 导入 CM 负责名单 | 单列 handle Excel，预览后逐行找群、找人，达标自动入库，其余人工核对 |
| 新加入的 Lark 人员 | 建立中性联系人，不自动判断为达人；没有独立新人员身份识别队列 |
| 已确认达人出现新材料 | 自动补配新 handle，不重判身份，不因此改负责人 |
| 人工对齐 handle 与 Lark 人员 | 权限、身份和账号冲突检查通过后，确认关系并加入当前 CM 的达人名单 |
| 确认达人或新增负责人 | 按有效负责人、授权和功能状态，补算最近七个英国日期的事件 |

导入使用 `creator-import-group-person-v5` 和代码内提示词，当前只读取群聊；账号补配使用 `creator-handle-research-v1.11`，读取群与私聊。两者尚未统一，图片与文件材料也尚未接入达人识别。

本轮只读配置：导入的 `enabled=false`，自动确认配置阈值 95%；现有导入由批次显式启动，执行器未以该标记作暂停条件，因此不能把它解释为所有导入已暂停。账号补配、负责人匹配、群分类与维护优先级启用，模型均为 `gpt-6-luna`。账号补配实际使用证据门槛，不使用配置中的百分比决定入库。配置会随后台修改变化，本版不启动导入批次、不更改开关或阈值。

## 3. 固定目标流程

```text
CM 负责名单导入 ── handle 规范化、去重、找会话与人员 ─┐
新加入联系人 ──── 登记联系人、读取本人业务上下文 ──┤
                                                    ↓
                                       复用既有事实、准备完整证据
                                                    ↓
                                  独立判断达人身份与精确账号关系
                                                    ↓
                       后端校验授权、材料、版本、人工结论和归属冲突
                              ┌─────────────────────┴────────────┐
                        写入成立的事实                  等待材料或人工核对
                              ↓
          账号补配、负责人匹配、群分类、维护优先级、七天事件补算

已确认达人 + 新材料 ── 复用身份与旧账号，只判断新增账号 ──┘
```

### CM 负责名单导入

当前上传支持 `.xlsx`，一个有数据的工作表、单列 handle，1–2,000 条、最大 2 MB；拒绝公式、宏、外链及数字单元格。保存原始值和规范化值，精确去重。

先复用已有人员与账号关系，不重复付费；对新账号找相关群或私聊及全部可能人员，再分别判断身份和账号。名单证明这是候选账号，不证明某个群成员就是本人。某行未找到人，保留未匹配记录，不新建空壳达人。

选定 CM 的负责名单是一项业务声明，入库后可以按现有规则为该 CM 增加负责关系；全量 Curva 目录不是负责名单，不能随上传者分配负责人。

### 新加入人员

同步首次发现就登记联系人，不因外部身份、群名或加入达人群直接确认。取得可读材料后纳入身份判断，不预先用自报账号关键词排除人员。没有可读文字单独记为等待材料；消息或相关资料变化后继续，不重复全库扫描。

有本人创作、直播或内容履约证据，可以先确认达人，handle 和负责人允许暂缺。账号有明确证据再关联；负责人不默认归给发现者。若现有人工身份或拒绝记录冲突，等待明确更正。

这是待实现入口：当前 Worker 只建立联系人，没有上述自动身份队列或 writer。

### 已确认达人

默认复用身份及同一人的精确已关联账号，只处理新账号。一个人可以有多个 handle、多个负责人；某个弱账号不影响其他强账号。主动复核才重新判断旧关系，不能因弱模型返回自动删除人工或正式事实。

现行数据库一个 handle 只能有一个正式 owner 联系人。多个 Lark 身份、共同账号、助理与代理不能自动合并；支持同 handle 多人需要另行定义关系并改造约束，不写成已经支持。

## 4. 识别准则

身份看本人创作业务，账号看本人关系。无需固定自我介绍；完整自然问答和“精确合作群名＋本人账号、直播或视频履约”可以成立。

不把商家审批、助理介绍、代运营、模板、转发、商品链接参数或邮箱当作本人账号证明。Curva 是辅助目录，不是入库门槛。账号证据的消息时点不等于平台当前实名、控制权或法律所有权。

身份确认、账号关联和负责人确认可以同时完成，也可分开成立。同一次模型请求可输出身份与多个账号的独立结论；后端分项处理，不必按每份文档增加一个 AI 请求。

## 5. 六份后台处理手册

后台入口：`/admin/assistant-rules` → “达人识别”，仅有效 Owner 可编辑。这组文档不进入 CM 或 Owner 的运营助手问题导航，避免识别规范被当作业务事实。

| 手册 | 固定职责 | 模型读取方式 |
| --- | --- | --- |
| [流程与入口](../../backend/app/assistant_rules/manuals/creator-recognition-flow.md) | 导入、新人、已确认达人分支及状态 | 服务端确定入口，不额外调用模型选路线 |
| [达人身份证据](../../backend/app/assistant_rules/manuals/creator-identity.md) | 本人创作身份、正反证、不确定 | 仅未确认人员需要 |
| [人员与账号关联](../../backend/app/assistant_rules/manuals/creator-handle-link.md) | 自述、问答、群名联合证据、多账号与冲突 | 仅需要判断新账号时读取 |
| [材料与补查](../../backend/app/assistant_rules/manuals/creator-evidence.md) | 问答、群与私聊、反证、有限补查及版本 | 取材阶段使用，模型只接收必要判断说明 |
| [入库与后续处理](../../backend/app/assistant_rules/manuals/creator-admission.md) | 权限、幂等、人工事实、负责人来源和事件补算 | 后端执行，不能让模型直接写库 |

任务接入后固定文档版本与材料指纹，文档更新只影响新准备的任务。发布手册不触发识别、付费调用、关系修改或全库重算。

## 6. 继续开发的顺序

1. 在现有导入和账号补配中接入这组手册的任务级快照，统一身份与账号含义，保留各自协议与硬校验。
2. 导入补齐私聊召回和自然业务问答，避免必须找到群才能找到人；以固定案例定向回归。
3. 在现有 Worker 的任务模式中增加新联系人身份处理，复用取材、授权校验与正式入库，不恢复旧泛扫、旧候选页面或三阶段流程。
4. 新身份确认后接现有下游信号；有负责人且消息可读才补算七天事件。
5. 验证新入口和人工保护后，只处理新发现或材料变化的对象；历史全量重跑单独启动。

首版保持文字证据；图片、文件复用已有材料队列作为后续接入，不新增 Agent 框架、向量数据库或另一套联系人库。不以额外限额代替证据复用和按变化处理。

提示词验收采用固定回归与独立样本分离的方式，符合 [OpenAI 官方模型优化指引](https://developers.openai.com/api/docs/guides/model-optimization) 中先定义评估、再根据真实输入迭代规则的原则；本版不新增外部评估服务或付费请求。
