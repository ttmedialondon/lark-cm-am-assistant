# 达人—Handle 自动匹配：队列与并发方案 v1.0

日期：2026-10-03

状态：第一阶段已实现；默认关闭、独立 Key 未配置；本轮验证未调用付费模型，不建立正式关联。

判定协议：[Prompt v1.2](creator-handle-association-prompt_v1.2.md) 与 [JSON Schema](creator-handle-association_v1.2.schema.json)。本方案替代上一份研究报告中以 Batch API 为默认执行方式的建议，不改变识别证据标准。

## 1. 确定的方案

### 第一阶段实际交付

- 配置：`/admin/ai` →「达人—handle 匹配」，独立加密 Key，默认模型 `gpt-5.6-luna`；需 Owner 主动开启。
- 任务：`/admin/ai/creator-handle-matching`，查看状态、建议及 token，取消、重新检查、一键补入全部未处理的已确认达人。
- 开启后的新达人自动排队；新消息、编辑、群名及授权变化合并唤醒。Curva 归档变化每分钟检查，重准备已登记人员，证据不变复用缓存。
- 默认全系统 3 个 API 名额；准备线程独立，最多 6 个 ready 包。单请求总截止 45 秒、租约 120 秒、最多 3 次网络尝试。
- 30 RPM、60,000 TPM、每日 1,000,000 token 为初始功能限额，可在配置卡修改；UTC 日界线。请求前保守预留，成功按 usage 结算；未知计费保留预留，未发网络请求释放。
- 本阶段只保存建议，身份、账号、负责人和旧关联均不修改；需额外上下文或存在冲突时留待复核，不暗中再开模型升级请求。
- 相同证据的终止失败也复用，不因无关消息重新付费尝试；只有 Owner 主动「重新检查」或材料/凭证变化才允许新的尝试。

额外只有一张轻量用量预留台账 `creator_handle_requests`，用于租约失效或旧响应时仍保留用量；不是第二套任务队列。RPM/TPM/日预算是本功能的本地保护，不能计入系统外对同一 OpenAI 项目的调用，也不是美元费用硬上限；供应商限流及项目账单设置仍须同时使用。其他 AI 功能共享全局并发及故障暂停，不共享本功能的每日预算。

Curva 源目录默认指向现有已核验归档；可用 `CURVA_CATALOG_PATH` 指定另一个完整目录。归档文件必须不可原地覆写，更新时整套换入含 SHA-256 的 manifest，应用只读；不可读取或校验失败时停在等待状态，不发送模型请求。消息的研究访问限制继续生效。

采用 **PostgreSQL 持久化任务队列＋现有 Python Worker＋受控并发 API**。

一个任务处理一位联系人，一次核对其多个候选 handle。Worker 可以同时处理不同人的请求，任何一个完成就补上下一项，不等待整批结束。

全库首次处理与后续新达人自动匹配使用同一条链路，只是任务来源和优先级不同：

`达人入库 / 新证据 / 全库任务 → 登记与合并任务 → 本地准备证据 → 并发 API → 校验结果 → 保存建议或符合规则的关联`

第一版不加 Redis、Celery、RabbitMQ 或 Kafka，也不把几十个人塞进一个模型上下文。数据库保证任务持久化，线程池负责同时发送请求。

**队列负责不丢任务；并发负责提高吞吐；证据压缩和去重负责省 token。三者不是同一件事。**

## 2. 与当前代码的关系

当前代码已经具备部分基础，但并不表示这项新功能已经存在：

| 已有机制 | 新方案如何使用 |
| --- | --- |
| `worker.py` 的 AI 线程池与轮询调度 | 增加新版匹配任务的领取和执行入口，继续与摘要、回复任务公平调度 |
| `ai_dispatch.py` 的全局上限、限速与配额暂停 | 新任务必须计入共享运行数，不能另开不受控的请求池 |
| 数据库任务领取、租约及 `SKIP LOCKED` 模式 | 沿用领取方式，任务记录使用新的按联系人协议 |
| `openai_client.py` 的 Responses 传输与安全日志 | 复用调用层；增加功能级 reasoning 设置及错误分类，不另引入 SDK 重试层 |
| 授权可读查询、证据引用和加密工具 | 复用访问边界及基础校验，补齐新版多 handle 的引用校验 |

旧 `creator_import_rows` 以导入批次、CM 范围和单 handle 为中心，不能直接承载新达人事件；旧 `_admit` 还会建立负责人关系，**新匹配流程不得调用它来写账号关联**。不恢复已退役的身份泛扫描、独立负责人识别或反向找 handle 流程。

## 3. 哪些情况自动产生任务

| 触发 | 处理方式 |
| --- | --- |
| 新达人身份被确认入库 | 在同一个数据库事务中登记匹配任务，事务提交后 Worker 才能领取；网页不等待 API |
| 新达人没有同步到可读消息 | 标记等待证据；消息或授权范围准备好后再唤醒，不先付费猜测 |
| 本人或相关问答出现新账号、备用账号、改名、转让线索 | 本地筛出有变化的联系人，合并触发一次复核；不是每条消息都请求 API |
| 相关群名、回复链或消息正文变化 | 使受影响的证据版本失效，重新准备；已经关联一个 handle 的人也能发现第二个账号 |
| Curva 归档底表更新 | 只优先唤醒涉及新增/移除候选 handle 的任务，不因版本号变化就付费重跑全库 |
| 全库首次处理 / 人工重新检查 | 分页登记任务，按同一队列运行，支持暂停与恢复 |
| 授权撤销、可见性缩小、达人身份被人工撤回 | 取消或停止受影响任务；不能继续调用或使用已失效证据 |

新消息同步事务只标记受影响人员，不在其中解密全部历史或调用 API。初期建议连续变化合并等待 30 秒，最长合并等待 2 分钟，避免消息持续到达导致永不执行；这是可调整的初始策略，不是已上线参数。角色入库任务可以立即准备证据。

另用现有 Worker 的低频检查补漏：查已确认达人中缺任务或等待条件已经满足的人员。角色、消息变化检查保留重叠范围并靠去重消除重复，不能只靠单一时间水位假定所有事务按时间顺序提交。

**默认自动化范围是已确认达人。** 全库研究可登记所有联系人，但未知身份只在检索出 Curva 候选后进行有范围的证据判断；没有候选不得恢复“让 AI 泛扫谁是达人”。

## 4. 任务队列与去重

任务使用 `creator_handle_jobs`，用量预留使用 `creator_handle_requests`，均不复制业务人员、达人、账号或负责人表。迁移为 `071_creator_handle_matching.sql`。

任务需要保存：

- 任务、联系人、来源、全库运行编号、优先级和状态。
- 期望处理版本、实际处理版本、证据指纹、检索水位、授权范围及 Curva/prompt/模型配置版本。
- 加密证据包、加密结果、真实消息引用；不在普通日志里保存正文。
- 下次可执行时间、尝试次数、运行租约与领取令牌、错误原因。
- 输入/输出 token、请求标识、耗时与费用统计。

用数据库约束保证**同一个联系人最多一项未结束任务**，包括等待证据和等待复核状态。新的触发合并进已有任务，而不是再排十个相同请求；已结束后需要重新处理时创建下一项任务并保留历史。

证据指纹覆盖联系人、候选 handle 集合、消息正文与回复关系、授权、Curva、prompt 和模型配置。若已成功处理的同一指纹仍有效，复用结果，不调用 API。仅无关消息变化而选中证据不变，也不重复调用。

任务执行时固定一个快照版本。新证据在请求期间到达，只更新期望版本，不修改正在发送的证据包。返回时若版本或领取令牌已过期，记录费用与失效原因，**不把旧结论作为最新关联写入**，再合并处理新版本。

## 5. 准备证据与并发执行

### 本地准备，不占 API 名额

按当前授权范围读取群名、本人消息、员工提问和回复链；检索 Curva 候选并保留反向证据。Curva 归档经核验后按版本加载一次，不为每人重新读八份 CSV。

初始准备并发保持 1，复用现有独立准备线程，不阻塞 Lark 同步。准备后的少量证据包进入 ready；待发送包数量建议不超过 API 并发的 2 倍，避免一次解密并堆积全库。瓶颈实测在准备阶段时再提高至 2，并同时控制数据库连接。

每人通常 1–5 个候选 handle、8–20 条有用消息；平均总输入 3,000 token、软上限 4,000 是预算目标，不是硬裁剪。问答、否定、时间、改名及具体 video_id 不可截丢。无文本、无候选或证据不足分别记录，不付费强行得出否定。

已确认达人传 `creator_known=true`，不再让模型重复判断其身份；使用 v1.2 的短编号、共用证据和简短 JSON 输出。

### API 并发，共享上限

初始沿用当前**全系统最多 3 个在途 AI 请求**。没有其他 AI 工作时，匹配可同时发 3 个；如果摘要或回复占用 1 个，则匹配最多占其余 2 个。不是每个功能各开 3 个，更不是每个 Worker 进程各开 3 个。

领取 ready 任务时，先在同一短事务中检查全局准入，锁住任务并设置 running、租约和领取令牌，随后提交。**网络调用在事务外执行**，避免整个 API 等待期间占着数据库事务。

准入还须按实际组织/项目及模型的 RPM、TPM 留出请求和估算 token 余量，并结合供应商响应头更新可用量。现有 `ai_dispatch` 主要控制并发和故障暂停，周期配额预留是实施时需要补齐的部分，不能将“有空线程”当成“还有 API 配额”。

哪个请求完成，就释放名额、保存其结果并领取下一项。沿用 Python `ThreadPoolExecutor` 即可，不必重写 asyncio 框架。

初始并发 3，稳定后依次测试 5、10。提高并发前须同时检查账户的请求/分钟、token/分钟、限流率、请求延迟及本地资源；更多线程不保证更快。[OpenAI 限流说明](https://developers.openai.com/api/docs/guides/rate-limits)

保留现有 AI 功能间公平轮询；匹配内部让日常增量优先，但每连续执行 4 项增量后，允许 1 项历史任务进入，避免历史全库永远排不到。这个比例是初期设计值，不是额外的并发名额。

## 6. 状态、失败与恢复

| 状态 | 含义与下一步 |
| --- | --- |
| queued | 已登记，等待准备 |
| preparing | 本地整理证据；失败可按错误类型重试 |
| ready | 证据已准备，等待 API 名额 |
| running | 请求执行中，拥有有效租约和领取令牌 |
| retry_wait | 可恢复故障，等到 not_before 后再领取，不占线程睡眠 |
| waiting_evidence | 缺消息/候选/上下文，靠新证据唤醒，不循环请求 |
| review_required | 冲突、代理、历史或出 Curva 等需人工处理；新证据可唤醒复核 |
| completed | 已保存有效建议或按启用的策略关联；不等于所有候选都匹配成功 |
| failed | 重试耗尽或无法自动处理，保留原因 |
| cancelled | 任务取消、权限失效或源范围被撤回 |

建议每个同一证据版本最多 3 次实际网络尝试，首轮包含在内；补充证据/升级模型是另一次有版本记录的语义复核，初期最多 1 轮，不能借此无限重试。

- 临时 429/503：遵守有效 `Retry-After`；无提示时指数退避加随机抖动，同时推迟队列准入。配额/账单问题暂停队列，不靠重试解决。队列管理重试时，不叠加 SDK 自动重试。[OpenAI 重试与限流说明](https://developers.openai.com/api/docs/guides/rate-limits)
- 网络超时/5xx：有界重试；格式/引用不合法、拒答或输出截断记录不同原因，不能写成“不是达人”。
- 授权、prompt 或模型配置改变：失效旧快照，重建证据，不直接重发旧包。
- 当前共享传输的 `Retry-After` 处理有 3,600 秒截断，且主要分类 429；实现时须修正为不早于有效服务端等待时间，并补充临时 503/5xx 分类。长等待落到 not_before，不锁住线程等待。

任务领取设置有界 HTTP 总截止时间；运行租约必须长于截止时间及写回余量。崩溃任务在确认超时并留有余量后才回收，返回结果须比较领取令牌。超时可能是“供应商已执行、客户端没收到”，因此只能保证业务结果幂等，**不能保证外部 API 绝不重复计费**。

暂停：停止新领取，在途请求可完成，但必须再次校验后才保存；取消：在途响应不得写正式关联。余额不足或费用阈值触发时走共享准入暂停，恢复后只处理未完成任务。

## 7. 结果写入边界

第一阶段自动完成检索、调用、校验和建议保存，**自动建立正式账号关系默认关闭**。独立验证通过并明确共享账号规则后，再开启强证据关联，不因模型置信度高就直接开放。

证据充分但关系复杂时，最多补充一轮上下文或升级模型；该复核仍经过同一队列与预算，不额外开隐藏请求池。没有可补证线索时留待复核，不反复换模型。

保存或关联前再次核验：

1. 所有候选返回一次，Schema 与编号合法，消息仍在有效授权范围。
2. 本人账号有本人确认或完整账号问答；不能只满足“引用中有人发言＋别处出现 handle”。
3. handle 精确命中当前 Curva，候选及引用版本没有过期。
4. 同一 handle 的其他联系人、当前关联、人工结论、代理/共享/历史信息没有冲突。
5. 若开放自动关联，对账号逐条锁定并使用数据库唯一约束；多人同时返回时只能产生有效结果或待复核，不能互相覆盖。锁定顺序固定，避免多账号互锁。

多人可以提到同一 handle，一人也可有多个 handle，但现有 owner 唯一约束不会因并发而失效。代理关系不写成本人 owner；自动增加账号不能删除现有账号或覆盖人工结论。

这项任务不自动修改达人身份、CM/AM 负责人或机构合作关系，不触发 Lark 群发/回复。关联写入产生的更新事件不再触发同指纹匹配，防止“匹配→入库→再匹配”的循环。

## 8. 速度、token 与费用

假设模型单次平均用时 L 秒，N 个联系人需要调用，实际可用并发 C，则理想 API 时间约为 `N × L / C`，再受准备、限流、重试及其他 AI 功能占用限制。

例如 1,000 人、每次 10 秒：串行约 2.8 小时，3 并发理想约 56 分钟，5 并发理想约 33 分钟。**这些是算术示例，不是系统实测或完成时间承诺。**

并发不会自动减少 token 或单次费用。省 token 仍靠一人多 handle 共用证据、Curva 本地检索、结果指纹复用、无需 API 的状态跳过，以及只对有证据的疑难项升级。

当前模型 `gpt-5.6-luna` 标准价为每百万输入 $0.20、输出 $1.20。按 3,000 输入＋300 计费输出 token 的假设，单次约 $0.00096，1,000 次约 $0.96；16,169 人全部各跑一次约 $15.5。输出须包含计费 reasoning，且不含税、地区附加、重试和升级。[官方模型价格](https://developers.openai.com/api/docs/models/gpt-5.6-luna)

普通并发不能套用上一版 Batch 折扣预算；同一输入输出预算下，当前模型 Batch 首轮约 $7.8，普通并发首轮约 $15.5。Batch 更省费用但采用异步完成窗口，不是“同时开多个普通请求”。本版优先低延迟，**第一阶段不同时实现两套执行器**；将来明确接受等待的历史离线任务再接 Batch。[Batch 官方说明](https://developers.openai.com/api/docs/guides/batch)

任务调度需要单轮/每日费用阈值，付费前预留预计费用，返回后按实际 usage 结算；异常请求计费不明时不直接释放全部预算。多人并发预留也必须原子检查，不能每个请求各自认为还有余额。实现和小样本验证前不承诺成本上限或准确率。

## 9. 实施顺序与验收

1. 新任务表、事件合并和补漏检查：先登记与准备，不调用模型。
2. v1.2 包构建/校验、共享准入及 Worker 并发接入：小样本允许调用，只保存建议。
3. 新达人/新消息自动触发、崩溃恢复、暂停与预算：验证全链路后开放日常增量。
4. 历史全库分页入队，与日常增量共享调度；不能只登记命中者，需分别统计无文本、无候选、受限与失败。
5. 独立留出集验证通过后，另行启用正式关联；共享 owner 规则未明确前维持人工确认。

扩展现有关键工作流测试，而不建另一套重复测试。最低验收：

- 同时触发同一人十次，只产生一项未结束任务；成功同指纹不再付费。
- 多人可以并行，但新匹配加摘要/回复的全局在途数不超过设定上限。
- 请求期间出现新消息、撤权、取消或换配置时，旧响应不能写入最新关系。
- 任务领取后重启能恢复；429/503 延迟不早于服务端提示，账单故障暂停。
- 无证据的人不会循环请求；已有账号的人新增第二个 handle 可以被发现。
- 同 handle 并发冲突不覆盖人工关系，不建立负责人、不恢复退役机制。
