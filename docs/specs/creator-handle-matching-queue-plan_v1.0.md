# 达人—Handle 自动匹配：队列与并发方案 v1.0

日期：2026-10-04

状态：已支持强证据自动建立正式账号关联；开关由 Owner 控制，普通规则发布不改变开关或主动重扫历史。v1.11 的 Curva 仅为辅助目录，未收录账号可通过精确群名或明确账号线索进入匹配。模型判断聊天含义，后端校验协议、引用、授权、证据来源关系和实际数据库冲突。

判定协议：[Prompt v1.11](creator-handle-association-prompt_v1.2.md) 与 [JSON Schema](creator-handle-association_v1.2.schema.json)。本方案替代上一份研究报告中以 Batch API 为默认执行方式的建议。

## 1. 确定的方案

### 第一阶段实际交付

- 配置：`/admin/ai` →「达人—handle 匹配」，独立加密 Key，默认模型 `gpt-5.6-luna`；需 Owner 主动开启。
- 任务：`/admin/ai/creator-handle-matching`，查看状态、账号匹配结果及 token，取消、重新检查、一键补入全部未处理的已确认达人。
- 开启后的新达人自动排队；新消息、编辑、群名及授权变化合并唤醒。Curva 归档变化每分钟检查，重准备已登记人员，证据不变复用缓存。
- 当前全系统 5 个 API 名额；准备线程独立，最多 6 个 ready 包。单请求总截止 45 秒、租约 120 秒、最多 3 次网络尝试。
- 不设置应用层 RPM、每分钟 Token 或每日 Token 上限。请求前记录保守用量估计，返回后记录实际 usage；未知计费保留估计，未发网络请求记为零。用量台账只记录，不据此拒绝或延后任务。
- 通过服务端强证据校验的本人账号自动建立正式关联；其他结果保留供复核。逐个 handle 处理，不修改达人身份、CM/AM 负责人或既有人工结论，不暗中再开模型升级请求。
- 相同模型输入的成功、待复核结果复用；密钥轮换、可读授权记录或原文 JSON 格式变化不单独触发新请求。同一凭证的终止失败也缓存；失败后 Owner 主动「重新检查」、实际材料/模型变化或更换凭证时允许新的尝试，避免沿用旧 Key 的账单/权限故障。

额外只有一张轻量请求与用量台账 `creator_handle_requests`，用于租约失效或旧响应时仍保留用量；不是第二套任务队列，也不充当费用上限。省 Token 依靠减少重复请求和有依据的取证，不依靠预算截停或固定每分钟限速；OpenAI 实际限流仍按响应头和 Retry-After 退避。其他 AI 功能继续共享全局并发及故障暂停。

Curva 源目录默认指向现有已核验归档；可用 `CURVA_CATALOG_PATH` 指定另一个完整目录。归档文件必须不可原地覆写，更新时整套换入含 SHA-256 的 manifest，应用只读。不可读取或校验失败时不使用其内容，以空参考目录继续处理明确合作群名和 TikTok 账号来源；目录状态变化使旧快照失效。消息的研究访问限制继续生效。

采用 **PostgreSQL 持久化任务队列＋现有 Python Worker＋受控并发 API**。

一个任务处理一位联系人，一次核对其多个候选 handle。Worker 可以同时处理不同人的请求，任何一个完成就补上下一项，不等待整批结束。

已确认达人的历史补入与后续新达人自动匹配使用同一条链路，只是任务来源和优先级不同：

`达人入库 / 新证据 / 历史补入 → 登记与合并任务 → 本地准备证据 → 复用缓存或并发 API → 校验结果 → 强证据正式关联，其余待核实`

第一版不加 Redis、Celery、RabbitMQ 或 Kafka，也不把几十个人塞进一个模型上下文。数据库保证任务持久化，线程池负责同时发送请求。

**队列负责不丢任务；并发负责提高吞吐；证据压缩和去重负责省 token。三者不是同一件事。**

## 2. 与当前代码的关系

以下现有机制已接入新匹配流程：

| 已有机制 | 当前使用方式 |
| --- | --- |
| `worker.py` 的 AI 线程池与轮询调度 | 增加新版匹配任务的领取和执行入口，继续与摘要、回复任务公平调度 |
| `ai_dispatch.py` 的全局上限、限速与配额暂停 | 新任务必须计入共享运行数，不能另开不受控的请求池 |
| 数据库任务领取、租约及 `SKIP LOCKED` 模式 | 沿用领取方式，任务记录使用新的按联系人协议 |
| `openai_client.py` 的 Responses 传输与安全日志 | 复用调用层；增加功能级 reasoning 设置及错误分类，不另引入 SDK 重试层 |
| 授权可读查询、证据引用和加密工具 | 复用访问边界及基础校验，补齐新版多 handle 的引用校验 |

旧 `creator_import_rows` 以导入批次、CM 范围和单 handle 为中心，不能直接承载新达人事件；旧 `_admit` 还会建立负责人关系，**新匹配流程不得调用它来写账号关联**。不恢复已退役的身份泛扫描、独立负责人识别或反向找 handle 流程。

## 3. 哪些情况自动产生任务

| 触发 | 处理方式 |
| --- | --- |
| 新达人身份被确认入库 | 在同一个数据库事务中登记匹配任务，事务提交后 Worker 才能领取；网页不等待 API |
| 新达人没有同步到可读消息 | 标记等待证据；消息或授权范围准备好后再唤醒，不先付费猜测 |
| 相关会话同步一页新消息 | 对相关已确认达人合并登记信号；之后准备材料和比较指纹，不在同步事务内调用 API |
| 相关群名、回复链或消息正文变化 | 使受影响的证据版本失效，重新准备；已经关联一个 handle 的人也能发现第二个账号 |
| Curva 归档底表更新 | 每分钟检查版本，重准备曾准备材料或等待名单的已登记人员；模型输入不变则复用缓存 |
| 历史补入 / 人工重新检查 | 历史补入一次读取并登记符合条件的已确认达人；单人重新检查立即登记，按同一队列执行 |
| 授权撤销、可见性缩小、达人身份被人工撤回 | 取消或停止受影响任务；不能继续调用或使用已失效证据 |

新消息同步事务只标记受影响人员，不在其中解密全部历史或调用 API。当前连续变化合并等待 30 秒，最长合并窗口 2 分钟；这是事件去抖，不是每分钟请求限额。新达人确认入库、人工操作可以立即准备证据。

Worker 每分钟补查最近一次配置保存时间以来新确认、且没有任何任务的达人。更早的存量达人由「补入全部未处理达人」登记；已有 completed、review_required、waiting_evidence 等任务的人不会被该按钮重复补入，只有无任务或仅有 failed/cancelled 的人符合条件。等待证据靠新消息、授权/群名变化、名单更新或人工重新检查唤醒，不定时付费重试。

**当前自动化和历史补入都只处理已确认达人。** 尚未提供全体未知联系人入队入口，不恢复“让 AI 泛扫谁是达人”。已有 handle 不排除后续匹配，以便发现第二个账号。

## 4. 任务队列与去重

任务使用 `creator_handle_jobs`，请求与用量记录使用 `creator_handle_requests`，均不复制业务人员、达人、账号或负责人表。迁移为 `071_creator_handle_matching.sql`；历史 RPM/Token 限额列保留但不再读取、配置或参与调度，无需破坏已有数据。

任务保存：

- 任务、联系人、来源和状态；增量与历史来源决定调度次序。
- 期望处理版本、实际处理版本、证据指纹、授权引用及 Curva/模型配置版本；prompt 版本参与指纹。
- 加密证据包、加密结果、真实消息引用；不在普通日志里保存正文。
- 下次可执行时间、尝试次数、运行租约与领取令牌、错误原因。
- 累计输入/输出 token、请求标识、创建/更新时间；台账分别记录每次尝试的估计与已知实际用量。

用数据库约束保证**同一个联系人最多一项未结束任务**，包括等待证据和等待复核状态。新的触发合并进已有任务，而不是再排十个相同请求；已结束后需要重新处理时创建下一项任务并保留历史。

缓存按同一联系人、实际模型输入、prompt、服务商、Project 和模型复用。消息原文、候选 handle、群名、角色、时间、回复链或缺口变化会改变输入；不因密钥轮换或仅存储格式变化重新付费。本轮授权及原文引用单独重建、实时校验，不复用旧授权；Curva 收录状态与输入快照一致，但未收录不阻止关联。仅未改变选中材料的消息变化不会产生新请求；普通消息若实际进入上下文，仍需重判，不能承诺所有无关聊天都零调用。

缓存结果也经过相同的正式关联门槛；仍有效的强证据可直接入库，无须再付费。缓存不是绕过当前授权、人工结论或账号冲突检查的捷径。

任务执行时固定一个快照版本。新证据在请求期间到达，只更新期望版本，不修改正在发送的证据包。返回时若版本或领取令牌已过期，记录费用与失效原因，**不把旧结论作为最新关联写入**，再合并处理新版本。

## 5. 准备证据与并发执行

### 本地准备，不占 API 名额

按当前授权范围读取群名、本人消息、员工提问和回复链，召回精确账号并保留反向证据。Curva 为普通账号词提供参考召回；专属合作群主号、明确 TikTok 账号表达和主页链接不要求目录收录。归档经核验后按版本加载一次，不为每人重新读八份 CSV。

准备并发为 1，复用现有独立准备线程，不阻塞 Lark 同步。ready 达到 6 包时暂停继续准备，避免一次解密并堆积全库。

本地读取本人最近最多 20,000 条可读 text/post 消息，结合父回复和群名检索精确 handle。普通裸单词仍只按 Curva 成员召回，不能把任意英文词当账号；明确账号来源可召回未收录 handle。本人消息、父消息、普通群名的召回权重分别为 4、2、1，精确固定合作群主名为 8，这不是归属置信度。最多选 12 个候选、48 条完整消息及 20,000 字符，并补充关键消息前后 5 分钟上下文。问答成组纳入，不截断单条正文。因容量限制丢失核心取证组合或已选外部账号线索时，按 handle 标记资料缺口；不再靠关键词判定遗漏是否是归属否认。此取证范围不是全文审阅。

已确认达人传 `creator_known=true`，不再让模型重复判断其身份；使用 v1.2 的短编号、共用证据和简短 JSON 输出。

默认按「联系人＋handle」过滤已经正式关联的账号，不按人员整项跳过。旧 Excel、自动确认和人工确认均免重复付费核验；新账号仍入候选。全部候选已关联则本地完成，不调用 API。已有账号只在主动「重新检查」或数据库实际冲突时复核，不用聊天关键词触发重查。正式关系快照变更时重建材料；来源标签不变，不把历史导入改成人工审核。

群名可用于找到候选。只要候选有精确群名或明确账号线索且本人有可读消息，就交给模型判断是否构成关联；没有可读文字或没有账号候选仍本地等待。Curva 是否收录单独记录，不能替代本人关系证明。礼貌消息、本人业务、代理、否认、转让等含义不在后端复判。完整原文、上下文和视频路径继续保留。

v1.10 保留 group_context 和现有队列，移除保存结果及页面展示时的关键词语义否决。模型判断账号自述、自然问答、否定对象、群内本人业务及反证；后端检查本人引用、精确账号或固定群主名、真实回复/私聊前驱链、有效授权、版本和实际账号冲突。关键词只辅助取证排序与提示，不决定关联。自动关联审计仍保留消息与会话名称哈希，不保存正文。版本变更使旧 ready 包及返回响应失效；历史待核实结果不自动升级或入库，需 Owner 主动重新检查。

### API 并发，共享上限

当前**全系统最多 5 个在途 AI 请求**。没有其他 AI 工作时，匹配可同时发 5 个；如果摘要或回复占用 1 个，则匹配最多占其余 4 个。不是每个功能各开 5 个，更不是每个 Worker 进程各开 5 个。

领取 ready 任务时，先在同一短事务中检查全局准入，锁住任务并设置 running、租约和领取令牌，随后提交。**网络调用在事务外执行**，避免整个 API 等待期间占着数据库事务。

准入只检查功能开关、有效证据快照、共享并发及供应商暂停/退避状态；不统计最近一分钟请求数，也不设本地 Token 预算。`ai_dispatch` 结合供应商响应头和 429/临时故障退避应对实际配额，不能将“有空线程”当成“供应商一定允许请求”。

哪个请求完成，就释放名额、保存其结果并领取下一项。沿用 Python `ThreadPoolExecutor` 即可，不必重写 asyncio 框架。

并发已从 3 提高至 5。继续提高前须同时检查账户的请求/分钟、token/分钟、限流率、请求延迟及本地资源；更多线程不保证更快。[OpenAI 限流说明](https://developers.openai.com/api/docs/guides/rate-limits)

保留现有 AI 功能间公平轮询；匹配内部每连续执行 4 项非历史任务后，优先让一项可执行历史任务进入。该规则在准备和领取阶段均已实现，不增加并发名额。

## 6. 状态、失败与恢复

| 状态 | 含义与下一步 |
| --- | --- |
| queued | 已登记，等待准备 |
| preparing | 本地整理证据；失败可按错误类型重试 |
| ready | 证据已准备，等待 API 名额 |
| running | 请求执行中，拥有有效租约和领取令牌 |
| retry_wait | 可恢复故障，等到 not_before 后再领取，不占线程睡眠 |
| waiting_evidence | 缺消息/候选/上下文，靠新证据唤醒，不循环请求 |
| review_required | 冲突、代理、历史或证据不足等需复核；新证据可唤醒，未被 Curva 收录本身不需复核 |
| completed | 本轮结果已处理；符合强证据门槛的账号已正式关联，不代表所有候选均匹配成功。以页面逐条「已关联」标记为准 |
| failed | 重试耗尽或无法自动处理，保留原因 |
| cancelled | 任务取消、权限失效或源范围被撤回 |

每个任务快照最多 3 次领取尝试，首轮包含在内；崩溃失联也消耗一次尝试。当前没有自动补证或自动升级模型的第二轮请求池。人工重新检查或实际材料/配置变化允许新的尝试。

- 临时 429/503：遵守有效 `Retry-After`；无提示时指数退避加随机抖动，同时推迟队列准入。配额/账单问题暂停队列，不靠重试解决。队列管理重试时，不叠加 SDK 自动重试。[OpenAI 重试与限流说明](https://developers.openai.com/api/docs/guides/rate-limits)
- 网络超时/5xx：有界重试；格式/引用不合法、拒答或输出截断记录不同原因，不能写成“不是达人”。
- 授权或模型/凭证配置改变：失效旧快照，重建证据，不直接重发旧包。prompt 版本在准备阶段参与缓存指纹；当前没有独立的 prompt 更新事件机制。
- 长 Retry-After 不截短，等待写入 not_before，不锁住线程睡眠。

任务领取设置有界 HTTP 总截止时间；运行租约必须长于截止时间及写回余量。崩溃任务在确认超时并留有余量后才回收，返回结果须比较领取令牌。超时可能是“供应商已执行、客户端没收到”，因此只能保证业务结果幂等，**不能保证外部 API 绝不重复计费**。

暂停：停止新领取，在途请求可完成，但必须再次校验后才保存；取消：在途响应不得写正式关联。供应商返回余额不足或账单配额故障时走共享准入暂停，恢复后只处理未完成任务；不因本地当日 Token 用量暂停。

## 7. 结果写入边界

功能启用后，检索、调用、校验和正式关联使用同一条队列。无需另一项开关；但模型判断“支持”不等于全部自动入库，不以置信度数字或匹配百分比作为门槛。

现有账号关系不发送给模型，也不作为本地候选召回来源；输出保存与页面展示时，检查其他正式 owner 和其他联系人最新建议中的账号声明，发现冲突即降为待复核。关系复杂或证据不足时等待补证或人工重新检查，不暗中换模型继续请求。

保存结果和建立关联前再次核验：

1. 所有候选返回一次，Schema 与编号合法，消息仍在有效授权范围。
2. 单条结果为 `supported / self_account / at_message`，理由是本人明确声明、完整账号问答或本人主页确认；`needed` 为空。服务端核对实际引用，不能只满足“引用中有人发言＋别处出现 handle”。
3. handle 有精确、可追溯的来源，候选及引用版本没有过期；Curva 未收录不构成否决。
4. 没有关键历史、候选或反证遗漏，且当前条目的问答和账号语境完整。同一 handle 的其他声明、正式 owner、人工结论、代理/共享/历史信息没有冲突。
5. 授权、群名、正文、身份、任务版本和领取令牌仍有效；过期响应只记录用量，不保存为当前建议。

每个 handle 独立决定：一人可关联多个账号；同一包里另一个弱证据账号不会阻止强证据账号入库，但全局关键证据遗漏会阻止本包自动关联。`operator`、`account_creator`、历史或不明确的关系只留结果，不写成本人 owner。

写库只增加当前联系人的 `owner / confirmed` 关系，并保留自动匹配来源、任务及审计引用。相同关系重复处理不重复创建；既有人工来源保留。已拒绝的关系、已有非 owner 关系、其他人的正式 owner 或当前账号级 CM/AM 关系不自动覆盖、转让或解除。现有正式 owner 唯一约束仍然生效。

页面「已关联」实时读取正式关系，不仅依据模型结果或历史任务状态。审计单独保留当时引用的原始消息编号、授权编号和正文哈希，不保存正文，也不随任务重跑而改变；不自动撤销已建立关系，后续反证交由人工复核。`at_message` 证明消息当时的自述，不证明今天仍控制该 TikTok 账号。

这项任务不修改达人身份、CM/AM 负责人或机构合作关系，也不触发 Lark 群发/回复。

## 8. 速度、token 与费用

假设模型单次平均用时 L 秒，N 个联系人需要调用，实际可用并发 C，则理想 API 时间约为 `N × L / C`，再受准备、限流、重试及其他 AI 功能占用限制。

例如 1,000 人、每次 10 秒：串行约 2.8 小时，3 并发理想约 56 分钟，5 并发理想约 33 分钟。**这些是算术示例，不是系统实测或完成时间承诺。**

并发不会自动减少 token 或单次费用。省 token 靠一人多 handle 共用证据、Curva 本地检索、结果指纹复用、无需 API 的状态跳过、短编号、固定 prompt 及简短 JSON 输出；当前不自动升级模型。

当前模型 `gpt-5.6-luna` 标准价为每百万输入 $0.20、输出 $1.20。按 3,000 输入＋300 计费输出 token 的假设，单次约 $0.00096，1,000 次约 $0.96；16,169 人全部各跑一次约 $15.5。输出须包含计费 reasoning，且不含税、地区附加、重试和升级。[官方模型价格](https://developers.openai.com/api/docs/models/gpt-5.6-luna)

普通并发不能套用上一版 Batch 折扣预算；同一输入输出预算下，当前模型 Batch 首轮约 $7.8，普通并发首轮约 $15.5。Batch 更省费用但采用异步完成窗口，不是“同时开多个普通请求”。本版优先低延迟，**第一阶段不同时实现两套执行器**；将来明确接受等待的历史离线任务再接 Batch。[Batch 官方说明](https://developers.openai.com/api/docs/guides/batch)

不设置应用层 RPM、每分钟或每日 Token 预算；费用控制依靠本地候选检索、共享证据、缓存和有界重试。每次尝试记录估计用量，返回后记录实际 usage；异常请求计费不明时保留估计，不能当作零消耗。单次输出仍最多 3,000 token，reasoning=none，不输出长分析；这是单次响应边界，不是吞吐限额。取消硬预算后不承诺每日费用上限，也不在独立验证前承诺准确率。

## 9. 验收与未实现范围

本阶段已实现任务持久化、事件合并、补漏、v1.2 证据协议、缓存、共享并发、重试、恢复、逐条强证据正式关联和结果展示；真实准确率尚未完成独立 API 验证。未知身份全库入队、历史分页登记、自动补证/模型升级仍未实现。

扩展现有关键工作流测试，而不建另一套重复测试。最低验收：

- 同时触发同一人十次，只产生一项未结束任务；成功同指纹不再付费。
- 多人可以并行，但新匹配加摘要/回复的全局在途数不超过设定上限。
- 请求期间出现新消息、撤权、取消或换配置时，旧响应不能写入最新关系。
- 任务领取后重启能恢复；429/503 延迟不早于服务端提示，账单故障暂停。
- 无证据的人不会循环请求；已有账号的人新增第二个 handle 可以被发现。
- 新响应和有效缓存均可自动关联强证据账号；同包弱证据保留待核实，不影响无全局缺口的强证据条目。
- 同 handle 并发冲突不覆盖人工关系，不建立负责人、不恢复退役机制。

记录队列等待时间、API 延迟、完成/待证据/待复核/失败数量、限流率和 token/费用。先找出实际瓶颈，再调整并发，不以“线程更多”代替测速。

当前页面按每位联系人的最新任务统计状态；待证据、待复核及失败不是匹配成功。尚未实现独立的全库运行编号或全库覆盖报表，不能将页面计数当作所有未知联系人的处理进度。
