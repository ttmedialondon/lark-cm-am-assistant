## 现在按什么做

| 文档 | 回答的问题 |
|---|---|
| [人员身份与达人名单](product/creator-management.md) | 人员六分类、负责人判断、handle 核实及 CM 候选入库 |
| [指定时段消息总结](product/message-summary.md) | 哪些消息要分析，P0–P3 怎么分，显示什么，哪些事不做？ |
| [后台权限与用户显示](product/admin-access.md) | 谁能看或修改哪些页面，领导能看哪些聊天，姓名和 @ 怎么显示？ |
| [系统技术说明](architecture/system-design.md) | 页面、同步、身份、账号、授权、并发和旧快照如何关联？ |

当前“人员目录”进行六类身份识别。第二步判断未归属达人与所选 CM 的业务关系，只有建议关联进入 CM 候选。第三步通过 OpenAI 核实 handle，高可信且无冲突的在自动开关开启后入库，其余由 CM 在前台补填确认。

单列 Excel 入口使用独立规则：整份表指定 CM 和名单属性，默认 CAP；先找 handle 精确对应群，没有则筛选相关群，由 AI 一起核对对应群和群内达人。有效身份直接复用，已确定的群合并去重后，唯一达人且无冲突就绑定入库，不再要求账号归属评分或本人发言证明。群不确定、没有识别到达人或有多位达人时，保留 handle 和名单属性，用户留空待核对。CAP／非 CAP／待定可在“我的达人”按人修改。已有数据和权限保留，消息总结仍关闭；不能把 API 成功率当识别准确率。

## 后续怎么维护

1. 同一条业务规则只改对应的那一份业务文档；技术文档说明实现，不再复制整份需求。
2. 新决定先写清“已确定、待确定、已实现”的区别。产品规则与代码不一致时标出差异，不自行按旧实现覆盖新决定。
3. 时段、人数、AI 开关和测试结果必须带日期；运行值以当前配置为准，历史快照不能当实时数据。
4. 旧版本从 Git 历史恢复，不再新增 `v0.x` 副本。导出的 PDF/Word 只用于分享，不另立规则来源。
5. 周报、复查、发布记录只追溯当时发生了什么；其中未来计划不自动转为开发任务。
