## 0. 一句话结论

项目已经不是“完全从零开始”。目前已经有一套可访问的 Lark 网页应用，员工授权后，系统具备发现其可见群、回填历史消息索引、持续增量统计和展示统计看板的代码基础。

但它现在仍是 **数据接入与统计原型**，不是完整的 AI 客服助手。当前没有读取和保存消息正文，没有 AI 分析、风险告警、TODO、知识库，也不会向 Lark 发送消息。

新版方案应在现有 Python 服务上继续演进，并把产品拆成清楚的阶段：

1. 先把授权、同步、退出删除、监控和备份做稳定。
2. 再决定是否、如何保存消息正文。
3. 实时消息接收与历史轮询并用。
4. 最后接入 AI 风险、TODO 和知识能力。

## 1. 为什么要重写技术方案

原 PRD 的核心假设是：机器人加入客户群，从入群时开始接收新消息，再做 AI 风险和 TODO。

实际验证发现了更有价值的路径：

- CM/AM 可以用自己的 Lark 账号授权网页应用。
- 系统可以按该员工本来就拥有的权限列出其可见群。
- 已验证可读取测试外部群的历史消息，不要求机器人先加入群。
- 因而数据起点不再只能是“机器人入群时间”，可以回填 Lark 在用户权限和平台保留范围内能够返回的历史。

这解决了历史数据和外部群接入问题，但不能单独解决实时告警。当前轮询默认每 3 分钟运行一次，无法满足原 PRD 的“几秒内告警”目标。未来如继续做实时风险告警，需要增加 Lark 事件/Webhook 通道，并保留轮询做历史回填和漏数补偿。

## 2. 当前到底已经有什么

### 2.1 已有能力

| 能力 | 当前状态 | 通俗说明 |
|---|---|---|
| 线上 HTTPS 入口 | 已部署、已验证 | 网站可以从公网访问。 |
| Lark 用户授权 | 已实现 | 员工点击授权后，系统以该员工身份读取其有权限的数据。 |
| OAuth 安全保护 | 已实现 | 使用一次性校验、PKCE 和安全 Cookie，降低授权码被冒用的风险。 |
| Token 加密存储 | 已实现 | Lark 的访问令牌和刷新令牌加密后才写入数据库。 |
| Token 自动刷新 | 已实现 | 短期访问令牌过期前，后台会使用刷新令牌续期。 |
| 群聊发现 | 已实现 | 枚举授权员工当前可见的群聊。 |
| 历史消息回填 | 已实现 | 按群分页读取历史消息，用游标支持中断后继续。 |
| 增量统计 | 已实现 | 首次回填后默认每 180 秒统计新消息。 |
| 去重 | 已实现 | 同一条消息重复拉取不会重复计数。 |
| 统计看板 | 已实现 | 展示群数量、消息总数、本人发送数、最近同步时间和任务状态。 |
| 不可读群处理 | 已实现一部分 | 后台会标记不可读群，但页面还没有清楚提示数据可能不完整。 |
| 审计基础 | 已实现一部分 | 已记录 OAuth 授权事件，尚未覆盖删除、暂停和管理员操作。 |

### 2.2 当前明确没有的能力

| 能力 | 状态 | 影响 |
|---|---|---|
| 保存消息正文 | 未实现 | 现在只能统计，不能理解客户在说什么。 |
| 图片、语音、视频、附件理解 | 未实现 | 无法分析非文本内容。 |
| AI 情绪与风险判断 | 未实现 | 没有 P0–P3、投诉或付款风险识别。 |
| 实时告警 | 未实现 | 不会把风险消息推送给 CM/AM。 |
| TODO 提取与定时汇总 | 未实现 | 不会自动生成行动项。 |
| 私聊查询 | 未实现 | 员工不能向机器人问“今天最重要的事情”。 |
| 知识库 | 未实现 | 没有正式知识、RAG 或自动问答。 |
| Lark 发消息/卡片 | 未实现 | 系统当前只读，不会主动回复或发通知。 |
| Lark 事件/Webhook | 未实现 | 编辑、很久以前的消息撤回和实时新消息不能可靠即时处理。 |
| 按群选择、暂停同步 | 未实现 | 授权后当前逻辑会同步用户可见的正常群。 |
| 退出登录、撤销授权、删除我的数据 | 未实现 | 这是正式试点前必须补齐的用户控制能力。 |
| 管理后台 | 未实现 | 目前没有管理员查看授权、异常群和任务的页面。 |

## 3. 当前用户流程

```text
员工打开网页
    ↓
阅读“只统计、不保存正文、不发消息”的说明
    ↓
点击“使用 Lark 授权”
    ↓
Lark 确认授权
    ↓
系统加密保存授权，创建首次历史回填任务
    ↓
后台发现群聊并分页统计消息
    ↓
员工在看板查看群数、消息数、本人发送数和同步状态
    ↓
后台约每 3 分钟继续做增量统计
```

当前页面的隐私承诺与代码一致：不保存消息正文、附件、@ 信息或完整发送者资料。未来一旦开始保存正文，必须先更新授权说明、隐私政策、数据保留和删除流程，不能静默改变数据用途。

## 4. 当前实际架构

```text
员工浏览器 / Lark 网页应用
            │ HTTPS + OAuth
            ▼
        Caddy 网关
            │ 仅转发到本机
            ▼
FastAPI Web（127.0.0.1:8100）
  ├─ 登录页与统计看板
  ├─ OAuth 回调
  └─ Web Session
            │
            ▼
        PostgreSQL
  ├─ 授权与加密 Token
  ├─ 用户可见群
  ├─ 最小消息台账
  └─ 同步任务与游标
            ▲
            │
独立 Python Worker ─────► Lark Open API
  ├─ Token 刷新
  ├─ 群发现
  ├─ 历史回填
  └─ 增量统计
```

### 4.1 技术栈

| 层 | 当前选择 |
|---|---|
| 后端 | Python、FastAPI、Uvicorn |
| 页面 | Jinja2、HTMX、Tabler |
| 数据库 | PostgreSQL、psycopg 3、原生 SQL |
| 后台任务 | PostgreSQL 任务表 + 独立 Worker |
| Lark 调用 | httpx 直接调用 Lark Open API |
| Token 加密 | AES-256-GCM |
| 公网入口 | Caddy、HTTPS |
| 进程管理 | systemd |
| 服务器 | Hetzner Ubuntu |
| 容器 | 当前未使用 Docker/Kubernetes |

这个规模下继续使用“单体 Web + 独立 Worker + PostgreSQL”是合理的。现在拆微服务只会增加部署、排错和运维成本；等用户量、消息量或团队规模明显增加后再评估拆分。

## 5. 两份代码分别是什么

### 5.1 当前主工程：`lark-message-stats`

这是现在应继续维护的实现。

```text
lark-message-stats/
├── app/
│   ├── main.py          # Web、OAuth、Session、看板
│   ├── worker.py        # 群发现、回填、增量、Token 刷新
│   ├── lark_api.py      # Lark API 封装
│   ├── crypto.py        # Token 加解密
│   ├── db.py            # PostgreSQL 连接
│   ├── config.py        # 运行配置
│   ├── templates/       # 页面模板
│   └── static/          # 页面样式
├── migrations/          # 数据库迁移
├── scripts/             # 迁移脚本
├── deploy/              # Caddy、systemd、Secret 录入
└── tests/               # 当前 4 个单元测试
```

### 5.2 历史工程：`lark-user-ingress`

这是早期 Node.js/TypeScript OAuth 骨架，保留了有用的 Lark 能力验证记录，但不应继续被描述为当前线上服务。

它的价值主要是证明：

- 用户 OAuth 路线可行；
- 授权用户可以读取其有权限的外部群及历史消息；
- 机器人不一定要加入群。

其中的 Node 服务只实现 OAuth 和加密保存 Token，没有群同步、消息回填、增量 Worker 和统计看板。当前 Python 工程已经覆盖并超过该骨架。

## 6. 当前数据设计与隐私边界

### 6.1 已有数据表

| 表 | 作用 |
|---|---|
| `oauth_states` | 保存一次性授权校验信息。 |
| `authorizations` | 保存用户身份、权限和加密 Token。 |
| `web_sessions` | 保存 30 天网页会话。 |
| `user_chats` | 保存用户可见群、同步状态和分页游标。 |
| `message_ledger` | 保存最小消息索引，用于计数和去重。 |
| `sync_jobs` | 保存回填/增量任务、租约、进度和错误。 |
| `audit_events` | 保存基础审计事件。 |

### 6.2 当前消息台账只保存

- 授权记录 ID；
- 群 ID；
- 消息 ID；
- 消息创建时间；
- 是否由当前授权员工发送；
- 是否被删除/撤回。

### 6.3 当前不保存

- 消息正文；
- 附件；
- @ 提及；
- 完整发送者资料；
- 客户、项目、风险、TODO、知识或 AI 输出。

这一边界降低了现阶段的隐私和合规风险，但也决定了当前产品只能做统计，不能做 AI 分析。

## 7. 安全设计

当前已有：

- OAuth v2 与 PKCE；
- 一次性 `state`，10 分钟过期；
- Secure、HttpOnly、SameSite Cookie；
- Session 和 OAuth state 仅保存哈希；
- Access Token 与 Refresh Token 使用 AES-256-GCM 加密；
- 刷新单次使用 Token 时使用数据库行锁，避免并发重复刷新；
- App Secret 不提交到 Git，通过服务器隐藏输入录入；
- PostgreSQL 和 FastAPI 不监听公网，只有 Caddy 暴露 80/443；
- Web 和 Worker 以低权限系统账户运行；
- Uvicorn 关闭访问日志，降低 OAuth 授权码进入日志的风险；
- Caddy 已配置 HSTS、`nosniff` 和 Referrer Policy。

正式试点前仍需补齐：

- 退出、撤销授权和删除数据；
- 数据保留期限与自动清理；
- 管理员权限和审计范围；
- Content-Security-Policy、防嵌入和前端依赖完整性；
- 密钥版本与轮换方案；
- 备份加密和恢复演练；
- 登录与 OAuth 接口的速率限制。

## 9. 当前主要风险

| 优先级 | 风险 | 为什么重要 | 建议 |
|---|---|---|---|
| P0 | 没有退出、撤权和删除个人数据 | 用户无法终止同步和清理数据 | 正式扩大试点前完成 |
| P0 | 没有明确的群选择确认 | 员工可能同时加入无关或敏感内部群 | 授权后先展示群列表，由用户确认启用 |
| P0 | 不可读群未在看板突出显示 | 用户可能误以为统计结果完整 | 显示不可读数量和数据完整性提示 |
| P0 | 消息权限名称记录不一致 | 旧文档与当前配置使用不同 scope 名称 | 以 Lark 后台和实际 OAuth 返回 scope 统一 |
| P1 | 没有监控、告警和备份恢复 | 故障或数据丢失可能不能及时发现 | 建立最小运维基线 |
| P1 | 自动化测试覆盖很少 | 分页、Token 刷新和并发错误难以及时发现 | 增加数据库与 Lark API 集成测试 |
| P1 | 同步任务表持续增长 | 每位用户每天约产生 480 条任务记录 | 增加归档、清理和聚合 |
| P1 | 看板实时执行全量计数 | 历史消息增长后页面可能变慢 | 增加汇总表或缓存 |
| P1 | 旧消息后续撤回可能漏更新 | 当前只轮询最近窗口，没有撤回事件 | 增加事件通道或定期对账 |
| P1 | 没有 Git 仓库和 CI/CD | 无法可靠审查历史、回滚和自动发布 | 尽快纳入公司 GitHub 组织 |
| P2 | 页面依赖公共 CDN | CDN 故障或供应链风险会影响页面 | 固定版本、增加 SRI/CSP 或自托管 |

## 10. 新版目标架构

如果继续实现原 PRD 的 AI 风险和 TODO，建议使用“实时事件 + 用户授权轮询”的混合方案。

```text
通道 A：Lark 用户 OAuth + Open API
  ├─ 员工授权与选群
  ├─ 历史消息回填
  ├─ 周期性增量同步
  └─ 漏数补偿与对账

通道 B：Lark 事件 / Webhook
  ├─ 实时新消息
  ├─ 编辑与撤回
  └─ 群、成员和权限变化

                 两个通道
                    ↓
          统一入站箱与幂等去重
                    ↓
       消息规范化、权限和数据隔离
          ├─ 原始数据与保留策略
          ├─ 固定风险规则
          ├─ AI 结构化分析
          ├─ 风险事件与 TODO
          └─ 未审核知识候选
                    ↓
       仅向授权内部渠道输出结果
```

为什么需要两条通道：

- OAuth 轮询擅长历史回填、外部群覆盖和漏数补偿。
- Webhook 擅长秒级新消息、编辑和撤回。
- 两者按稳定业务键去重后，才能同时兼顾完整性和实时性。

事件通道是否能覆盖真实跨租户群、是否要求机器人在群内，仍需单独做 Lark Spike。未验证前不能把“秒级风险告警”承诺为已具备能力。

## 11. 建议实施路线

### Phase 0：数据接入与统计原型（当前）

- 用户 OAuth；
- 群发现；
- 历史与增量消息索引；
- 统计看板；
- Token 加密和自动刷新；
- 单机 Hetzner 部署。

目标：证明 Lark 用户授权读取路线可行。

### Phase 1：可控试点

- 真实 CM/AM 端到端验收；
- 授权后的群列表与逐群确认；
- 暂停、恢复、退出、撤销和删除数据；
- 不可读群及数据完整性提示；
- 数据保留与自动清理；
- 日志、指标、故障告警、数据库备份和恢复演练；
- GitHub、代码评审、CI、部署和回滚流程；
- 补齐分页、重试、Token 刷新、并发和权限测试。

目标：让小范围员工可以安全、稳定、可退出地使用统计功能。

### Phase 2：正文与实时消息能力

- 确认消息正文的业务必要性、授权文案、保留期和删除传播；
- 明确只同步哪些客户群，默认不采集无关内部群；
- 增加 Webhook/事件入站和签名校验；
- 建立统一消息入站箱、幂等键和编辑/撤回模型；
- 原文最小化存储、加密、访问审计和敏感信息处理；
- 验证外部群、退群、撤权和群解散边界。

目标：建立可供 AI 使用、同时可审计和可删除的数据层。

### Phase 3：AI 风险与 TODO

- 固定规则先行的 P0/P1 兜底；
- AI 结构化输出与严格 Schema 校验；
- 风险状态、确认、关闭和超时升级；
- TODO 提取、定时快照和私聊查询；
- 内部通知目标与群映射；
- 脱敏评测集、质量指标、成本上限和模型切换层。

目标：实现原 PRD 的核心业务价值，但不自动回复客户。

### Phase 4：知识沉淀

- 原始依据、结构化事实、候选知识分层；
- 人工审核、来源追溯和失效传播；
- 正式知识库与 RAG；
- 建议回复，必须经人工审批后才能发送。

目标：在数据治理和 AI 质量稳定后，逐步形成可复用的公司知识。

|---|---|---|---|
| D-01 | 第一阶段产品定位 | 先完成“安全可控的统计试点” | 当前代码已经接近该目标，最快能交付真实用户价值。 |
| D-02 | 采集方式 | OAuth 轮询 + 后续 Webhook 混合 | 同时兼顾历史完整性和实时性。 |
| D-03 | 是否保存消息正文 | Phase 1 暂不保存；Phase 2 单独审批 | 一旦保存正文，隐私、合规和安全责任明显增加。 |
| D-04 | 授权后同步范围 | 用户明确选择客户群 | 不应在无提示情况下同步员工所有可见群。 |
| D-05 | 数据保留期 | 元数据先定 90 天试点值，评审后确认 | 需要控制风险和数据库增长。 |
| D-06 | 首批试点人数 | 3–5 名 CM/AM | 足够覆盖真实场景，又便于人工支持和纠错。 |
| D-07 | 实时告警目标 | Webhook Spike 后再承诺 | 当前 3 分钟轮询不能承诺秒级。 |
| D-08 | 多租户方向 | 当前只服务本公司；SaaS 另立项目 | 现有数据模型未包含完整租户命名空间。 |
| D-09 | 技术栈 | 继续 Python/FastAPI | 当前代码和部署已经存在，无充分理由立即重写。 |

## 13. Phase 1 验收标准

只有以下项目通过，才建议把当前原型称为“可控试点”，而不是“生产系统”：

1. 至少 3 名真实 CM/AM 完成 OAuth，并确认群数和消息统计基本正确。
2. 用户可以在同步前看见群列表，只启用明确选择的客户群。
3. 不可读、退出、解散或失权群有清楚状态，不会被展示成完整的零数据。
4. 用户可以暂停同步、退出登录、撤销授权并发起删除个人数据。
5. Token 刷新、分页断点、重试退避和服务重启续跑通过自动化或可重复测试。
6. 数据保留与清理任务生效，旧 Session 和同步任务不会无限增长。
7. 数据库自动备份成功，并完成至少一次恢复演练。
8. Web、Worker、数据库、同步失败和磁盘容量都有监控与告警。
9. 代码进入公司 GitHub 组织，主分支受保护，CI 自动运行测试和静态检查。
10. Lark 权限以当前后台实际授权和 OAuth 返回 scope 为准完成最小化复核。
11. 安全与隐私说明与真实行为一致，并由产品负责人确认。
12. 形成部署、回滚、故障处理和人员离职/撤权操作手册。
