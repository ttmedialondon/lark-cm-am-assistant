## 0. 执行摘要

本产品是一套基于 CM/AM 明确授权的 Lark 会话运营辅助系统。系统在非工作时段持续记录授权范围内的客户群消息，将需要在次日跟进的内容整理为可追溯的待关注事件，并通过网页工作台和 Lark 摘要展示紧急程度、判断依据和建议动作。

在相同授权和数据治理约束下，系统还会在后台回填 Lark Open API 实际可提供的历史群聊数据，形成受控的原始语料和候选知识，为后续知识库建设准备数据。过渡阶段接入 OpenAI 或 DeepSeek，为待关注事件生成仅供内部使用的回复建议，用于验证准确性和积累人工反馈；本阶段不自动向客户发送回复。

一句话原则：**系统先帮助团队“看全、排好、写出建议”，暂不替代 CM/AM 做业务承诺或自动回复。**

## 1. 背景与目标

### 1.1 业务背景

CM/AM 需要同时维护多个客户、达人和项目群。下班后产生的咨询、投诉、催办、付款或交付信息容易分散在不同对话中，第二天依靠人工逐群翻查，既耗时，也可能遗漏高风险事项。

与此同时，公司希望在员工明确授权、权限隔离和可删除的前提下，逐步沉淀历史沟通语料，为客户知识、项目经验、常见问答和业务规则的后续整理建立可靠的数据基础。

### 1.2 产品目标

1. 在每日 18:30 至次日 10:00 的非工作时段内，同步授权范围内的群聊消息，并按客户、项目和业务主题合并为待关注事件。
2. 在次日上午通过网页工作台展示完整结果，并可通过 Lark 消息发送重点摘要和工作台入口，帮助 CM/AM 快速确定处理顺序。
3. 为每个事件提供清晰的紧急程度、判断理由、原始消息依据和建议下一步动作。
4. 在 CM/AM 明确授权后，以不打扰聊天的后台方式回填授权范围内的历史群聊数据，为后续知识库建设准备可追溯语料。
5. 接入 OpenAI 或 DeepSeek，为待关注事件生成可编辑的回复建议，并通过人工采用、修改和放弃数据评估 AI 的准确性与业务价值。
6. 建设“夜间事件工作台”和“数据沉淀看板”，分别回答“今天先处理什么”和“数据同步与知识准备进展如何”。

### 1.3 非目标

- 本阶段不自动向客户、达人或外部群发送 AI 回复。
- 不允许 AI 自动确认价格、付款、合同、交期、法律或安全事项。
- 不把“出现 CM/AM 回复”自动等同于“事件已处理”。
- 不在未经授权或超出原有 Lark 权限的范围内读取消息。
- 首期不包含 P2P 单聊；图片、语音、视频和附件内容解析不纳入首期验收。
- 候选知识未经人工审核，不得直接用于正式知识库问答或自动回复。
- 消息分析结果不得用于员工绩效考核或对客户进行人格画像。

## 3. 用户、范围与关键口径

### 3.1 用户角色

| 角色 | 主要职责与权限 |
|---|---|
| CM/AM | 完成授权；查看本人权限范围内的事件、原始依据和回复建议；更新事件状态 |
| 团队负责人 | 在授权范围内查看团队汇总、分配负责人、处理升级事项 |
| 产品/运营 | 配置业务规则、评估事件识别与回复建议效果；默认无权查看无关群原文 |
| 系统管理员 | 管理应用配置、同步任务和故障；不得因运维角色自动获得业务正文权限 |
| 安全/合规 | 审核权限、保留期限、供应商和删除流程；按需查看审计记录 |

### 3.2 数据范围

“所有消息”在本文件中的准确含义为：**CM/AM 已明确授权、本人原本有权访问、且 Lark Open API 实际可返回的群聊消息。** 完整度会受到用户权限、群类型、平台保留范围和接口能力限制。

首期处理范围：

- 同步授权用户当前可见的群聊及平台可返回的历史群消息。
- 全量记录可读取消息的必要索引和状态；正文分析首期以文本消息为主。
- 不可读取群、读取失败、零消息和未授权必须显示为不同状态。
- 同一群被多名 CM/AM 授权时，消息应在公司数据层去重，并通过授权关系控制可见范围。

### 3.3 时间口径

- 默认团队时区：`Europe/London`，自动适配英国夏令时。
- 每日业务窗口：前一日 18:30（含）至当日 10:00（不含）。
- 10:00 关闭上一夜主窗口；迟到数据完成同步后应补入工作台并标记“延迟到达”。
- 周末、英国公共假日及团队特殊工作日规则可配置，正式上线前由业务确认。
- 窗口外消息可继续进入授权历史语料，但不进入当日夜间事件主清单。

## 5. 产品原则

1. **授权优先**：所有读取、保存、分析和模型调用均以明确授权、最小权限和原有数据可见范围为前提。
2. **工作台为准**：网页工作台是事件状态的唯一可信来源；Lark 消息是摘要和访问入口。
3. **按事件组织**：系统将同一客户、项目或问题的相关消息合并为事件，避免逐条消息形成重复待办。
4. **结论可追溯**：每个事件、紧急程度和回复建议必须关联原始消息；无依据时标记“待人工确认”。
5. **人始终负责**：AI 只提供辅助判断和草稿，不得自动关闭事件、确认业务事实或向客户发送消息。
6. **不确定性可见**：系统不能确定是否已经解决时，不得隐藏事件，应显示置信度和待确认信息。
7. **基础能力可降级**：AI 不可用时，消息同步、规则分级、事件列表和人工处理仍应正常运行。
8. **用途受控**：历史语料和候选知识不得超出授权说明的用途，不得用于未经批准的外部模型训练。

## 6. 总体流程

```text
CM/AM 阅读授权说明并完成 Lark 授权
        ↓
发现其权限范围内可读取的群聊
        ├── 历史消息回填 → 原始语料层 → 数据沉淀看板
        └── 持续增量同步
                    ↓
筛选每日 18:30—次日 10:00 的消息
                    ↓
去重、上下文关联、参与者识别和同主题事件合并
                    ↓
业务规则 + AI 判断事件类型、紧急程度和待确认信息
                    ↓
夜间事件工作台
        ├── 次日上午生成 Lark 摘要和工作台链接
        └── 为待关注事件生成内部 AI 回复建议
                    ↓
CM/AM 查看、确认、处理并反馈建议质量
```

## 7. 功能需求

### FR-001 授权与数据范围管理

- 授权页必须明确说明读取范围、正文处理目的、保存期限、第三方模型使用情况、撤销方式和删除方式。
- 系统只能读取授权用户本来有权访问且 Lark API 可返回的数据。
- 用户可查看当前授权状态、授权版本、已发现群、可读群、不可读群和最近同步时间。
- 用户应能选择或排除群聊，并可暂停同步、撤销授权和申请删除数据。
- 授权或权限失效后立即停止新增读取；后续数据处理遵循保留和删除策略。
- 同一群被多人授权时不得重复分析或重复通知；访问权限按用户、团队、客户和项目关系计算。

### FR-002 历史回填与持续同步

- 首次授权后，后台分页回填授权范围内且平台可返回的历史群消息；回填过程支持暂停、续传、失败重试和进度查看。
- 回填完成后持续进行增量同步，目标新鲜度 P95 不超过 5 分钟。
- 保存 `message_id`、群、时间、发送者标识、消息类型、回复关系、编辑/撤回状态及必要正文。
- 重复消息不得重复入库；编辑后重新分析；撤回、删除或来源权限失效后，派生事件、AI 建议和候选知识必须同步失效。
- 不支持解析的消息类型仍保留必要元数据，并明确显示“内容未解析”。
- 同步失败、权限不足、不可读群和零消息不得混为同一状态。

### FR-003 夜间消息窗口

- 系统持续同步数据，但仅将 18:30—次日 10:00 窗口内的消息纳入当日夜间事件主清单。
- 每个窗口使用唯一业务日期，确保重复调度不会产生重复事件或重复摘要。
- 对跨越窗口边界的同一对话保留必要上下文，但不得把无关历史内容重复计入当日数量。
- 10:00 后到达的迟到数据应补入原窗口，并记录补偿时间和影响的事件。
- P0 是否在夜间立即通知值班渠道由独立开关控制；在值班责任和升级路径未确认前，不默认打扰下班员工。

### FR-004 待关注事件识别与紧急程度

系统按客户、项目、对话主题和时间邻近关系，将多条相关消息合并为一个事件。每个事件至少包含：

- 事件标题、摘要和事件类型；
- 客户、项目、来源群和负责人；
- 首次出现时间、最近更新时间和所属夜间窗口；
- 紧急程度、判断理由、规则命中和 AI 置信度；
- 相关原始消息、上下文及跳转入口；
- 是否出现 CM/AM 回复，以及仍待确认的事实；
- 建议下一步动作和 AI 回复建议；
- 当前状态、操作人和状态更新时间。

紧急程度定义：

| 等级 | 业务定义 | 默认处理方式 |
|---|---|---|
| P0 紧急 | 人身安全、诈骗、账号/隐私安全、法律风险、重大舆情或严重付款风险 | 工作台置顶；是否夜间升级由值班规则决定 |
| P1 高优先级 | 强烈投诉、明确当日时限、重要客户持续催办、履约或付款异常 | 次日上午优先处理并突出展示 |
| P2 常规待处理 | 常规咨询、资料补充、排期确认和一般跟进 | 进入普通待处理列表 |
| P3 仅供了解 | 感谢、确认收到、普通闲聊或无需行动的信息 | 默认折叠，可查询 |

事件状态采用：`待人工确认`、`已查看`、`已处理`、`无需处理`、`误报`。

“未处理”的 MVP 判定原则：

1. 系统识别出明确问题、请求、投诉、风险、付款/交付事项或需要内部行动的内容时，先创建“待人工确认”事件。
2. 是否出现 CM/AM 回复作为独立事实展示，仅用于排序和提示，不自动证明业务已经解决。
3. “已处理”“无需处理”和“误报”只能由授权人员确认；AI 不得自动设置。
4. 同一主题后续仍有催办、风险升级或新事实时，应更新原事件并重新计算紧急程度。

### FR-005 次日上午结果呈现

- 每日上午 10:00 关闭上一夜主窗口，并在 10:05 前完成主汇总。
- 网页工作台保存完整事件列表；Lark 消息发送重点摘要、数据状态和工作台链接。
- 摘要至少包含 P0/P1 数量、待人工确认总数、最高优先级事件、数据更新时间和同步异常提示。
- 没有事件时明确显示“本周期未发现待关注事件”。
- 同步或分析失败时显示失败范围和最近成功时间，不得输出虚假的空列表。
- Lark 摘要默认不包含不必要的敏感正文，详情需进入有权限的工作台查看。
- 摘要发送目标支持本人私聊、团队群或负责人群配置；具体默认值在上线前确认。

### FR-006 AI 回复建议

- 通过统一模型适配层接入 OpenAI 或 DeepSeek，供应商、模型和路由策略可配置、可切换。
- 对 P0—P2 待关注事件生成 1—3 条内部回复建议，并标明待确认事实、风险点和建议动作。
- 回复建议必须基于关联原消息和必要上下文，不得编造身份、金额、日期、库存、项目状态或承诺。
- 涉及价格、合同、付款、法律、安全、隐私或明确承诺时，显示高风险提示；必要时只给处理框架，不生成可直接发送的完整话术。
- 建议仅在内部工作台或授权私聊中展示，CM/AM 可以查看、复制、编辑、采用或放弃。
- 本阶段不提供自动发送能力，AI 自动向外部会话发送次数必须为 0。
- 记录 `provider`、`model`、`prompt_version`、来源消息、置信度、耗时、成本和人工反馈，用于离线评测和后续迭代。
- 模型超时、限流或输出不合规时降级为业务规则和固定模板，不影响事件清单。

### FR-007 夜间事件工作台

工作台至少提供：

- 昨夜待关注事件总数和 P0—P3 分布；
- 待人工确认、已查看、已处理、无需处理和误报数量；
- 按负责人、客户、项目、群、等级、状态和时间筛选；
- 事件详情、判断依据、原始消息、数据新鲜度和 AI 回复建议；
- 同类事件合并、重复事件提示和迟到数据标记；
- 按日、周查看事件量、积压量、确认时间和处理趋势；
- 同步失败、分析失败和权限失效提示。

### FR-008 数据沉淀看板

该看板用于数据治理和知识库准备，不用于员工绩效评价。至少提供：

- 已授权用户数、授权版本和授权状态；
- 已发现、可读、不可读、排除和暂停同步的群数量；
- 已同步消息量、覆盖时间范围、最近同步时间和增量延迟；
- 历史回填进度、失败任务、重试状态和来源失效情况；
- 可形成结构化事实和候选知识的消息/事件数量；
- 客户、项目、常见问题和业务主题分布；
- 删除请求、权限变更、保留期限和处理状态；
- 模型调用量、费用、延迟、失败率和回复建议使用情况。

管理总览默认不直接展示大批原始消息正文；只有具备相应业务权限的人员才能进入具体事件查看来源。

### FR-009 知识库准备

| 数据层 | 内容 | 本期状态 |
|---|---|---|
| 原始语料 | 经授权读取的正文、角色、群、时间、回复关系和状态 | 受控入库 |
| 结构化事实 | 客户、项目、需求、问答、决定、承诺、规则和适用时间 | 自动提取，需可追溯 |
| 候选知识 | 常见问答、流程、客户偏好、项目规则和常见异议 | 默认未审核 |
| 正式知识 | 经人工确认后可用于检索或回复的内容 | 不属于本阶段 |

规则：

1. 原始对话是证据，不等于已确认事实。
2. 结构化事实和候选知识必须关联有效来源；无依据不得生成。
3. 客户或项目专属内容不得自动提升为全局知识。
4. 候选知识未经人工审核不得用于正式问答或自动回复。
5. 编辑、撤回、删除、授权撤销或来源权限失效必须传播至派生数据和未来索引。
6. 未经批准，不得把公司消息用于训练外部模型。

## 8. 数据对象与状态

| 对象 | 关键字段 |
|---|---|
| 授权 | 用户、授权版本、权限范围、授权/过期/撤销时间、状态 |
| 群 | Lark 群标识、客户/项目归属、可读状态、授权关系、最近同步时间 |
| 消息 | 消息标识、群、发送者、时间、类型、正文、回复关系、编辑/撤回状态 |
| 事件 | 业务日期、主题、摘要、等级、状态、负责人、来源消息、更新时间 |
| 回复建议 | 事件、建议正文、模型/提示版本、置信度、风险提示、人工反馈 |
| 候选知识 | 类型、内容、适用范围、来源消息、审核状态、有效状态 |

所有派生对象均必须保留来源关系和权限关系，禁止通过复制数据绕过原始访问控制。

## 9. AI 方案与评测

采用“业务规则 + 模型适配层 + 人工反馈”的组合方案。

| 组件 | 职责 |
|---|---|
| 业务代码 | 授权、隔离、去重、窗口、固定风险规则、事件状态、排序、发送和审计 |
| 大模型 | 事件聚合建议、摘要、紧急程度建议、待确认信息和回复草稿 |
| 评测体系 | 脱敏样本集、版本对比、人工评分、线上反馈和回归测试 |

模型要求：

- 仅发送完成任务所需的最小上下文，按规则脱敏敏感字段。
- 输出必须通过 JSON Schema、枚举、长度和来源校验。
- 群消息视为不可信输入，不得改变系统规则、越权取数或触发外部操作。
- OpenAI 与 DeepSeek 的数据地域、保留策略、是否用于训练和合同条款须完成安全与法务评审。
- 上线前使用不少于 300 条脱敏样本评测，覆盖中英文、混合语言、投诉、付款、交期、安全和无行动场景。
- 先以“影子模式”生成但不发送建议，再进入小范围人工使用；自动回复属于后续独立项目，必须重新评审。

## 10. 数据、权限与合规

1. 明确告知并记录授权版本、时间、权限范围、正文处理目的和模型供应商。
2. 采用最小权限原则，并按用户、团队、客户和项目进行数据隔离。
3. 提供群范围选择、暂停、撤销授权、导出和删除能力；删除须覆盖原文、事件、AI 输出、候选知识和未来索引。
4. 原始消息、访问令牌和敏感字段加密保存；Token、密钥和消息正文不得进入普通日志。
5. 发送给模型的内容必须最小化并按策略脱敏；未经批准不得用于供应商训练。
6. 对访问、导出、模型调用、删除、权限变更和状态操作记录审计日志。
7. 授权失效后停止新增读取；删除与保留行为按已批准的数据治理规则执行。
8. 原始正文默认仅对具有业务权限的人员开放，管理员或分析人员不因角色自动获得全文权限。
9. 多人授权同一群时，需明确公司数据层的去重、共同可见范围和单人撤销后的数据处理规则。
10. 正式保存正文前，必须更新当前授权页中“仅统计、不保存正文”的旧说明，并重新取得适用授权。

## 11. 异常、降级与非功能要求

### 11.1 异常与降级

| 异常 | 系统行为 |
|---|---|
| 授权失效或权限不足 | 停止新增读取，标记影响范围并提示重新授权 |
| 单个群不可读 | 标记“不可读”，不把它计为零消息，不影响其他群同步 |
| 历史回填中断 | 保存游标并安全续传，展示进度和最近错误 |
| 增量同步延迟 | 展示数据新鲜度和影响窗口，恢复后补偿同步 |
| 消息编辑/撤回/删除 | 更新原始状态，并使受影响的事件、建议和候选知识失效或重算 |
| AI 超时、限流或格式错误 | 重试后降级为规则和固定模板，不影响事件列表 |
| Lark 摘要发送失败 | 工作台保持可用并重试发送，禁止回退到外部客户群 |
| 数据源不可用 | 明确显示失败，不返回假空列表 |
| 重复调度或重复授权 | 按业务键幂等处理，不重复入库、分析或通知 |
| 未授权访问或导出 | 拒绝请求，不返回数据，并记录审计日志 |

### 11.2 核心指标

| 类别 | 指标 |
|---|---|
| 同步完整性 | 在授权且接口可读范围内，唯一消息同步完整率 ≥ 99.5% |
| 数据新鲜度 | 增量消息至工作台可见 P95 ≤ 5 分钟 |
| 晨间汇总 | 每日 10:05 前完成上一夜主汇总，成功率 ≥ 99% |
| 结果追溯 | 事件、等级和回复建议关联有效来源比例 100% |
| 去重与隔离 | 重复入库、重复事件、重复摘要和跨客户数据泄漏均为 0 |
| 风险识别 | P0 强制测试场景零漏判；P0/P1 测试集召回率目标 ≥ 95% |
| AI 稳定性 | 结构化输出重试后成功率 ≥ 99.5%，失败可降级 |
| 回复建议 | 自动向客户发送次数为 0；试点期“采用或轻微修改后采用率”目标 ≥ 60% |
| 权限安全 | 未授权读取、越权展示和跨租户泄漏均为 0 |

| AC-10 安全 | 跨客户隔离、审计、密钥保护、供应商策略和越权拒绝测试通过 |
