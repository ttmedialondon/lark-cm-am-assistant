# 消息风险识别与事件紧急程度规范 v1.0

日期：2026-09-08。来源：Shuxuan Li 提供的新分级定义及本期范围说明。

状态：**P0—P3 业务定义已记录；工程处理方案为待讨论建议，尚未实现或启用。**

本文件优先于旧 PRD/TDD 中冲突的分级、颜色及回复建议要求；未冲突的授权、数据保护和可追溯原则继续保留。

## 1. 本期范围（已明确）

当前只识别**事件紧急程度**，输出 P0/P1/P2/P3 及可核对的判断依据。

本期不做：

- 内部回复提示、回复草稿、推荐话术、自动安抚、自动追问或自动收集信息。
- 向达人、CM 或群聊自动发送业务消息。
- 根据识别结果自动执行后台操作、承诺付款、创建业务执行待办、认领达人或改变负责人。
- 自动关闭事件、认定已经处理完成，或重新开启已停用的达人识别/负责人匹配。

原始定义中的“AI 介入”保留为后续业务愿景，见第 3 节，不是本期要建设的功能。P0 必须立即人工处理的业务要求保留，但本次文档记录不等于已经接通人工告警渠道。

本轮仅更新需求文档，不改变运行代码、数据库、模型配置、生产任务或通知。

## 2. 新版业务定义（用户提供的标准）

### P0 — CRISIS

核心定义：重大风险，涉及合作关系或资金危机，必须立即由人工处理。

典型情况：

- 达人要求 unlink / terminate / leave agency。
- Paid collaboration / flat fee 未付款、金额错误或付款纠纷，**不包括普通 affiliate commission**。
- 严重投诉。
- 明确表示要 escalate / report。
- 威胁终止合作或不再与机构合作。

### P1 — ISSUE

核心定义：已经发生异常、风险或明显升级，需要人工判断和优先处理。

典型情况：

- Violation / Warning / Appeal。
- TikTok 账号异常、封禁、LIVE 或其他权限问题。
- Affiliate commission 异常。
- 商品、链接、流量等异常，已经影响 LIVE 或短视频的正常产出/销售。
- 达人明显生气、着急、不满。
- 同一问题反复催促。
- 明确提出的需求 **≥3 天无人回复/处理**。

### P2 — ACTION / INFORMATION

核心定义：正常业务请求或有价值的运营信息，需要记录、补充资料、执行或后续跟踪。

典型情况：

- Voucher 申请或相关问题。
- Sample 申请、补样、样品进度。
- 想要某个特定商品 / SKU。
- 发送 Product Link，希望申请商品或合作。
- 发送 Video Link，希望投流 / boost。
- FS / LE / Campaign 资源申请。
- 想 link / join agency。
- 询问或报名活动、campaign。
- “今晚会 LIVE”“明天会发视频”“视频已经发布”等运营信息同步。
- 其他需要记录、执行或后续跟进的正常业务信息。

### P3 — ROUTINE

核心定义：纯礼貌性或结束性沟通，没有新的有效运营信息，也基本不需要管理。

典型情况：

- Thanks / Thank you。
- Got it / Okay。
- Perfect / Amazing。
- No worries / Sounds good。
- 👍 / ❤️ / 🙏。
- Good morning / Have a nice weekend。
- 对已经解决的问题进行简单确认，如 “All sorted, thanks!”。

### 跨级原则

- 一旦包含值得记录、执行或跟进的**新信息**，就不再属于 P3，至少进入 P2。
- P2 不等于必须回复；有运营价值的信息同步也属于 P2。
- P2 中出现已发生的异常或明确升级，进入 P1；出现 P0 危机情形，进入 P0。
- Paid collaboration / flat fee 与 affiliate commission 必须区分，不能把所有付款/佣金消息统一视为 P0。
- 展示使用等级文字及含义，不仅依靠颜色：P0 红、P1 橙、P2 黄、P3 绿。

用户给定的判例：

| 消息 | 等级 |
|---|---|
| “Thanks!” | P3 |
| “Thanks, I’ll go LIVE tonight.” | P2 |
| “Got it, I’ll post tomorrow.” | P2 |
| “Thanks, but my account still can’t go LIVE.” | P1 |
| “I’ve had enough, I want to unlink.” | P0 |

## 3. 原始 AI 介入设想（完整留存，本期不启用）

| 等级 | 原始设想 | 本期边界 |
|---|---|---|
| P0 | AI 只负责识别，立即转人工，不自行处理 | 识别并标明 P0；不生成回复，不自行处理；人工通知机制另行确定 |
| P1 | AI 先安抚并收集必要信息，CM 优先处理 | 仅识别 P1，不生成安抚/追问或收集信息话术 |
| P2 | AI 的主要介入层级：先回答并收集完整信息；需要后台操作时整理信息并创建 CM 待办 | 仅识别 P2，不回复、不自动追问、不创建执行待办 |
| P3 | AI 可自动简单回复，或根据场景无需回复 | 仅识别 P3，不生成或发送简单回复 |

P2 后续原则：需要 CM 操作时，AI 应尽量先收齐 Product Link、Video Link、SKU、品牌、具体需求等，避免 CM 二次追问。**当前只保留此需求，不实施信息收集或回复环节。**

## 4. 建议的识别口径（待讨论，不冒充已确认规则）

### 4.1 按事件判断，消息只是证据

- 一条新消息可以触发判断；工作台以“同一项业务问题/请求/运营事项”为识别单元，而不是每条消息创建一条重复告警。
- 同一线程内“想申请样品 → 补 Product Link → 补 SKU”优先归为一个 P2 请求。
- 同群不等于同事件；不同达人、不同商品或不同问题不能只因时间接近而合并。
- 一个消息涉及两个独立问题时允许拆成两个事件；同一事件同时满足多个条件时，取最高有效紧急程度。
- 同一问题跨天延续，不因夜间窗口或日期改变而重新建事件。日期是展示维度，不是事件身份。
- 首期不自动跨群合并；有依据时显示“可能相关”，由人工确认。

### 4.2 结合上下文，不做关键词计数

- 识别实际说话人、当前意图、引用、否定、历史叙述和已解决情况。例如达人明确要求解除机构关系才是 unlink 红线；商品链接操作、否定句或引用别人的历史话语不能仅因出现 unlink 就判 P0。
- 只询问付款安排，不等于已经发生未付款或付款纠纷；付款类型不明时标记待核对，不能猜成 flat fee 或 affiliate commission。
- 严重投诉与一般不满、威胁向上升级与普通“报告一个问题”需要业务例子校准，不能只凭 report、urgent 或感叹号判断。
- “Thanks” 不能覆盖同一事件仍未解决的 P0/P1 证据；单条消息的礼貌性质与事件风险并不等价。
- “All sorted” 可作为解决迹象，但识别器不自动改变人工处理状态；历史已解决风险也不应仅因再次被引用就新建紧急告警。
- 明显情绪、催促和异常用于判断这次事件，不输出达人性格画像或员工绩效结论。

### 4.3 P2 分清请求与信息，不增加新等级

两类都保持 P2，但在识别事实中区分：

- **ACTION：** 明确请求，如申请样品、希望投流、申请 voucher。
- **INFORMATION：** 运营信息，如今晚 LIVE、明天发视频、已经发布。

“无人回复/处理 ≥3 天”的条件作用于明确请求，不自动作用于无需回应的运营信息。仅有链接、图片或含糊表达时，结合上下文；信息不足应标记待核对，不一律当 P3。

### 4.4 三天升级由程序计时，不让模型猜日期

建议记录首次明确请求时间、与该请求有关的有效回应、处理事实及数据覆盖状态：

- 从该请求起点计算，后续催促不重置计时；“同群 CM 发过任意消息”不等于回应了该请求。
- “已回应”和“已解决”分别记录；“收到 / 我看看”不自动表示已完成。
- 必须定时复核未完结请求，即使没有新消息，也能发现达到阈值的事件。
- 同步失败、回填不全或授权失效时，显示“回复/处理情况未知”，不能把没采集到消息当作无人回应的证据。
- 3 天具体按连续 72 小时、自然日期还是工作日计算，以及“已回复但未处理”的计时方式，尚待业务确定，不在代码里自行固定。

### 4.5 不确定性与紧急程度分开

- `needs_review` 表达证据不足或边界不清，不是第五种业务等级，也不是一项低风险判断。
- 已有充分 P0 事实时，其他资料缺失不能将其降级；无法可靠判定的消息保留人工核对，不因模型失败默认归入 P3。
- 证据不足时可保持等级未定及待核对状态；如果已有充分 P1/P2 事实，则保留该等级并说明未知项。
- 来源编辑/删除、权限撤销或新事实改变结论时需要重新评估，保留变更依据；“最高曾达等级”与“当前等级”不要混为一谈。

## 5. 推荐的最小工程流程（待评审，尚未开发）

授权消息及有效上下文 → 同问题事件归并 → 结构化语义识别 → 业务规则/时间校验 → 保存等级与证据 → 只读人工核对。

1. **输入：** 复用现有已授权消息、发送者、时间、root/parent/thread、编辑/删除状态；只带本事件必要上下文，不把整个聊天库交给模型。
2. **归并：** 新消息优先更新已有问题，去重使用原始消息标识及事件版本；按同群、明确线程/引用和业务主题保守归并。
3. **模型：** 一次结构化识别输出事件事实、等级建议和来源引用，不生成回复或解决方案。提示中的聊天正文只作为数据，不执行其指令。
4. **程序：** 负责权限、消息有效性、重复提交、时间计算和已确认业务红线；不能把裸关键词命中当作已确认的 P0 事实。已确认的 P0 红线不允许模型自行降级。
5. **结果：** 展示等级、简短事实性理由、证据和未知项；允许人工核对分类，暂不接外发通知或自动业务执行。
6. **定时复核：** 专门检查明确请求的逾期条件，不依赖又来一条消息才能升级。

建议的最小结果字段：

| 字段 | 用途 |
|---|---|
| event_id / revision | 关联同一问题及其本次版本，避免重复事项 |
| severity | P0 / P1 / P2 / P3；确实无法判断时为空并待核对 |
| event_type / is_explicit_request | 区分危机、异常、正常请求和运营信息；支持正确的逾期判断 |
| reason / evidence_message_ids | 简短分级依据及可追溯原消息，使用 `(chat_id, message_id)` 复合引用；不是回复或操作建议 |
| needs_review / unknowns | 指明资金类型、历史覆盖或语义等缺口 |
| first_request_at / response_evidence / handling_evidence | 仅明确请求使用，用于三天规则；未知不伪装为否 |
| assessed_at / policy_version / model_version | 支持重算、复核与追溯 |

不提供 `reply_suggestion`、回复正文、安抚话术、自动发送参数或自动处理指令。等级不替代人工处理状态；完整的接单、完成、交接工作流不纳入当前分类阶段。

### 与当前系统的接法

- 复用 FastAPI/Jinja 前台、PostgreSQL、现有消息同步及授权读取。此阶段不因旧架构规划而引入新前端框架、消息中间件或 RAG。
- 增加独立的事件紧急程度模块/任务类型；不要用“达人身份识别”或“负责人匹配”任务代替，不恢复它们的停用开关。
- 先对一个业务范围做只读对照评估，评估入口和展示授权另行确定。可优先讨论 Remi 范围，但本文件不启动扫描、不把本次权限自动扩给其他人。
- 达人/handle/群的归属不确定与事件紧急程度是两回事：有权读取的风险证据可进入待核对，但不能据此自动判定达人身份或归属 CM。
- 若目标是 P0 及时人工接入，不应只在第二天早晨分析；建议连续处理已同步新消息，夜间窗口只用于汇总。通知渠道、值班与响应时限须另行确定。

## 6. 当前工程基线与缺口（代码检查，不代表新功能上线）

已有：

- 消息按 `(chat_id, message_id)` 去重，保存加密正文、时间、发送者和线程/引用结构。见 `backend/app/worker.py`、迁移 `004` / `005` / `009`。
- 当前有效授权、正文同意、会话可见/同步范围及逐条消息观测校验。见 `backend/app/creator_review.py`。
- 联系人及当前负责人、开始/结束时间；仍不是完整的“handle—工作群”确认关系。见迁移 `017` 及 `creator-account-review-live-v0.2.md`。

未实现：业务事件表/分类器、P0—P3 识别任务、同问题持续归并、业务请求有效回应/完成判断、三天逾期复核、人工告警接入。旧 PRD/TDD 对这些内容的描述只是目标设计。

需要处理的输入缺口：

- `contact_assessments._readable_body` 只抽取 `text` 字段，富文本 `href` 可能丢失。P2 的 Product Link / Video Link 识别应保留结构化链接信息，但不自动打开、抓取链接。
- `creator_review._text_content` 是脱敏展示文本，可能遮挡长数字。分类输入不能直接复用页面展示文本；应从有效授权原始正文构造最小必要输入，保留与判断有关的金额、SKU、链接类型，同时移除不必要个人信息和链接凭据。
- 默认增量同步配置为 300 秒，不是消息发出即被实时识别。实际延迟还包含回填、排队和模型时间；不能对“立即人工”做尚未具备的实时承诺。
- 群内其他人员发言、跨群处理或离线处理可能使“无人回复/处理”不完整，必须区分事实与未知。

## 7. 评估与验收建议（实施前校准）

先做人工标注集和影子评估：系统仅输出分类供对照，不发消息、不自动创建业务执行任务。模型选型、阈值及准确率承诺在评估后决定，不先承诺“已准确”。

必须覆盖：

| 场景 | 预期或需校准的点 |
|---|---|
| 第 2 节五条原始判例 | 严格满足 P3 / P2 / P2 / P1 / P0 |
| 明确 flat fee 未付款/金额错误；affiliate commission 异常 | 分别 P0、P1，不混淆费用类型 |
| 正常 voucher/sample/资源申请、申请 join agency | P2；加入与退出机构不能混淆 |
| 账号封禁、LIVE 权限异常、违规/申诉 | P1，若另有 P0 事实则按危机处理 |
| 明显不满、同一问题反复催促 | 按 P1 标准；“反复”的次数/时间还需校准 |
| 发送有业务意图的 Product/Video Link | 至少 P2，不因无普通文本当作 P3 |
| 纯感谢，及感谢同时附带新运营信息 | P3 与至少 P2 分开 |
| 明确请求跨越三天，且没有新消息 | 达到已确定时间口径后能复核升级；信息同步不误触发 |
| CM 在同群回答另一个话题 | 不当作此请求已回应或解决 |
| 否定 unlink、引用历史风险、已经解决的问题 | 依据上下文，不机械关键词升级 |
| 同群多个达人/多个问题、跨日续催、共享群重复同步 | 不混合、不重复、不重置请求起点 |
| 缺历史、权限撤销、模型失败、正文编辑/撤回 | 显示未知/失效并重算，不静默归 P3 |
| 先有 P0/P1，后面收到 Thanks | 不用礼貌性尾句直接覆盖未解决事件 |

分别统计 P0/P1 漏判与误报、P2 信息漏收、错误 P3、重复/错合事件及人工改级原因。事件证据可追溯、越权读取为零、回复生成/发送次数为零是硬性验收边界。

## 8. 待讨论决定

1. **三天口径：** 连续 72 小时、自然日还是工作日？“已有有效回复但仍未处理”的升级条件是什么？
2. **P0 人工接入：** 谁负责、通过哪个内部入口、是否夜间值班、识别后多久必须确认？不能沿用旧版“次日上午再看”来解释重大危机。
3. **语义边界样本：** 严重投诉 vs 一般不满、真正 escalate/report vs 报告问题、重复催促的最小条件，以及费用类型不明时的核对方式。
4. **首期识别范围：** 哪些已授权群/单聊、是否只选确定的达人范围，怎样处理未确认 handle 及共享群中的其他参与者？

本文件没有把这些未决项伪装成已批准规则，也没有更改目前真实核对页或服务器运行状态。
