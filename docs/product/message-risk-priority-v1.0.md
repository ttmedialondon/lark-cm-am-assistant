# 下班消息总结助手｜通俗需求版

更新日期：2026-09-10。状态：需求已更新，功能尚未开发或启用。

本文件是本期需求基准；旧 PRD/TDD 中与它冲突的实时告警、回复建议等要求不再适用。已有的数据保护和权限限制继续保留。

## 1. 我们要做什么

CM 上班后，不用从头翻一晚上的聊天，就能知道：**哪个达人说了什么、现在进展怎样、哪些事要先看。**

例如，总结前一天 **18:00 到当天 10:00** 的消息，按 P0—P3 排好，在 CM 的前端展示。这个时间只是例子，实际上下班时间、时区和周末规则还要确定。

流程很简单：

**下班时段的消息 → 按同一件事整理 → 总结并分级 → 上班后人工查看**

这是下班消息总结助手，不是全天实时预警系统。P0 的危机含义不变，在总结里排最前；本期不提供夜间即时告警，也不承诺半夜有人接手。

## 2. 四个等级怎么分

| 等级 | 通俗理解 | 常见情况 |
|---|---|---|
| 🔴 P0 — CRISIS 危机 | 合作或资金出了大问题，必须人工处理 | 要退出机构、解除或终止合作（unlink / terminate / leave agency）；固定合作费（paid collaboration / flat fee）未付款、金额错误或纠纷；严重投诉、明确威胁升级投诉或举报（escalate / report） |
| 🟠 P1 — ISSUE 异常 | 已经出问题，需要优先处理 | 违规、警告、申诉、封号或 LIVE 权限异常；普通带货佣金（affiliate commission）异常；商品、链接、流量问题影响产出或销售；明显生气、着急、不满；同一问题反复催促；明确请求满 3 天无人回复/处理 |
| 🟡 P2 — ACTION / INFORMATION 请求或信息 | 正常业务，需要跟进，或者值得记下来 | Voucher、样品、补样及进度、商品/SKU、投流申请；Product Link / Video Link 携带的合作或 boost 请求；FS / LE / Campaign 资源申请和活动报名；想加入机构；今晚直播、明天发视频、视频已发布 |
| 🟢 P3 — ROUTINE 日常 | 没有新事项的礼貌或结束语 | Thanks、Okay、Perfect、问候、👍 / ❤️ / 🙏，或对已解决问题的简单确认 |

三个容易混淆的地方：

- **固定合作费纠纷是 P0；普通佣金异常是 P1。** 只问付款安排不等于付款纠纷，费用类型不明就标“待核对”。
- **有新运营信息，至少是 P2。** “Thanks!” 是 P3；“Thanks, I’ll go LIVE tonight.” 是 P2；“Thanks, but I still can’t go LIVE.” 是 P1。
- **看实际意思，不数关键词。** 想加入机构是 P2，明确要退出是 P0；普通“反馈一个问题”不等于威胁举报。

## 3. CM 打开前端看到什么

先显示本次总结的时间范围、更新时间，以及消息有没有同步完整。

每件事只讲清楚：

**达人 / handle → 发生了什么 → 下班时段内的最新进展 → 等级和简短原因**

例如（虚构示例，不是真实聊天）：

> @example_creator：申请样品，随后补充了商品链接。CM 已回复“收到，我看看”，暂未看到办理完成的消息。P2：正常样品申请。

P0 排最前，其次 P1、P2；P3 默认折叠。等级不只靠颜色区分。

有人回应、正在跟进、对方表示已解决，都要在总结里说明。**“已回复”不等于“已解决”**，AI 不替人工关单；未解决的 P0/P1 也不能因为最后一句是“谢谢”就变成 P3。遇到不确定的地方直接写“待核对”，不装作已经确定。

## 4. 总结时要守住哪些规则

- 只整理对应 CM 有权读取的达人相关聊天。建议首轮从已确认的达人名单开始；名单编辑权不自动增加消息查看或 AI 扫描权限。
- 以时段内发出的消息为本次总结范围；之前的消息只补充必要背景，不重新算成这次的新事项。时段结束后的新回复不写成“下班期间已处理”。
- 同一件事的申请、补链接、补 SKU、催进度合成一条；不同达人、不同问题不要混在一起。同一问题跨天仍保持关联，不每天当成全新问题。
- 一个 Lark 用户关联多个 handle，不等于每条消息都属于所有账号；没有说清哪个账号，就保留账号未明，不重复计数或猜负责人。
- 有商品/视频链接的消息不能因为文字少就漏掉；图片、语音等未解析内容要说明看不全，不能默认判 P3。
- 同步不全或 AI 判断失败时显示缺口，不把“没采集到回复”写成“没人回复”。迟到同步的消息按原发送时间补回对应总结，更新版本，不重复生成事项。

## 5. 这期不做什么

不生成回复建议、草稿或话术，不自动回复、追问、发通知，不代办业务、承诺付款或自动创建执行待办；也不自动认领达人、改负责人、关闭事件或恢复旧自动识别功能。

先把总结和分级展示出来，让人检查是否准确。已有消息同步、达人关联和 AI 调用基础可以复用，不需要为这一步重做整套系统。

## 6. 还有哪些需要确定

1. **时间：** 每位 CM 的上下班时间、适用时区、周末/节假日怎样算，以及总结何时生成。
2. **范围和查看人：** 先给哪位 CM 试用、哪些群聊/私聊纳入、谁可以查看总结和相关原消息；未确认达人怎样处理。
3. **三天规则：** 按连续 72 小时还是工作日？已回复但一直没处理怎么算？从原请求开始算，跨天总结不重置；只对本次总结涉及的事项结合历史判断，不默认增加全天催办系统。规则未定前不自行启用按时长自动升级。
4. **人工纠错：** 第一版怎样反馈错判、谁能改级，以及后续 AI 更新怎样保留人工结论。

上线前用一小批人工核对的消息检查：有没有漏掉 P0/P1、把运营信息误当闲聊、合错事项，或把“有人回应”误写成“已经解决”。
