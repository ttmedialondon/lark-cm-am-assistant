## 四个等级

| 等级 | 怎么理解 | 常见情况 |
|---|---|---|
| P0 · CRISIS 危机 | 合作关系或资金有重大风险，必须人工处理 | 要求 unlink / terminate / leave agency，威胁终止合作；paid collaboration / flat fee 未付款、金额错误或付款纠纷；严重投诉，明确威胁 escalate / report |
| P1 · ISSUE 异常 | 已经出问题，需要优先判断、处理 | Violation / Warning / Appeal、封号、LIVE 或其他账号权限异常；affiliate commission 异常；商品、链接、流量问题影响产出或销售；明显生气、着急、不满；同一问题反复催促；明确请求满 3 个工作日仍未获有效回应，需要足够历史证据 |
| P2 · ACTION / INFORMATION 请求或信息 | 正常业务请求，或值得记录、执行、跟进的新信息 | Voucher；样品、补样及进度；特定商品 / SKU、Product Link 合作申请；Video Link 投流 / boost；FS / LE / Campaign 资源及报名；想 link / join agency；今晚 LIVE、明天发视频、视频已发布等运营同步 |
| P3 · ROUTINE 日常 | 没有新事项的礼貌或结束语 | Thanks / Okay / Perfect / Amazing、问候、👍 / ❤️ / 🙏，或对已解决问题的简单确认 |

分级时记住：

- 固定合作费未付或纠纷是 P0；普通带货佣金异常是 P1。只问付款时间不等于纠纷；费用类型不明就标“待核对”。
- 有新运营信息，至少 P2：“Thanks!” 是 P3；“Thanks, I’ll go LIVE tonight.” 是 P2；“Thanks, but I still can’t go LIVE.” 是 P1。
- 看实际意思，不数关键词。加入机构是 P2，明确退出是 P0；普通反馈不等于威胁举报。引用、假设或第三方遭遇不自动算成该达人的危机。
- 最后一句“谢谢”不能抹掉未解决的 P0/P1。“有人回复”不等于“已经解决”；“All sorted”只能记作对方表示已解决，AI 不自动关单。
- 无法判断就标“待核对”，必要时不定级，不能把附件看不懂、同步失败或 AI 失败当作 P3。

## CM 会看到什么

页面先显示总结时段、更新时间、处理进度和资料缺口，再按事件列出：

**达人 handle / Lark 用户 → 发生了什么 → 时段内最新进展 → 等级 → 相关原文。**

P0 最先看，其次 P1、P2；P3 默认折叠。事件没有明确指向某个账号时，页面显示该达人名下已确认的 handle（多个并列），不再因 AI 未指定账号而显示横线；没有正式账号关联时才显示横线。等级不只靠颜色区分。

页面分别列出检查到的相关群聊与私聊数量、所选时段实际有材料的会话数；每项事件展示对应会话名称与类型，方便核对多群和私聊是否纳入。只有历史、时段内没有相关消息的会话不制造事件。

私聊中的 Remi 主动消息可以归纳。群聊里，达人当日未发言时，明确回复、准确 @，或可靠 AI 群关联且完整成员信息确认只有一位可能达人时，仍可形成事件；多人或对象不明的群消息不硬归给某个人。

同一会话里，同一个人的同一件事，申请、补链接、补 SKU、催进度合并成一条；不同人、不同问题不混在一起。一个 Lark 用户有多个 handle，没说清账号就不猜具体事件属于哪个账号，也不把同一事件复制到所有账号；页面的并列账号仅表示已确认属于同一达人。

## 这期不做什么

只总结、分级和展示原文，不生成建议回复、草稿或话术，不自动回复、追问、发通知、承诺付款或创建业务待办；不自动认领达人、改负责人、关闭事件或恢复旧识别功能。

回复助手、其他 CM、每日自动生成、人工改级、法定假日，以及跨会话或跨日报长期追踪，均须另行确认，不因讨论而自动上线。

## 重新启用时怎么执行

以下流程用于主人明确要求的固定时段分析。

1. 先准备并确认 Remi 名单；主人到 `/admin/ai#offhours-summary` 核对 OpenAI Project、模型、API Key 和本轮时间。密钥留空会保留原值。
2. 未开启只保存，不调用 AI；开启并保存成功后立即排队，无须再点“开始”。前端在 `/dashboard/offhours-summary` 查看结果。
3. AI 直接整理事件，不必逐条人工批准后才显示。不同会话并行，所有 AI 功能共用最多 3 个请求并发；限速等待，配额异常明确暂停，失败有限重试。
4. 时段未结束时只看已同步部分。保持开启时约每分钟检查本时段变化；通常检查至结束后 24 小时，结束后才保存开启则从保存起检查 24 小时。再次保存也可延长检查期，不无限扫描。
5. 迟到消息按原发送时间补入；内容或相关范围变化时替换该会话的当前版本，已成功的相同输入不重复付费分析。失败可保存重试，过期后需主人再次保存检查。

## 必要的技术与安全限制

- 每轮最多 300 个先按已确认达人相关性筛选的会话；每会话最多 200 条时段内消息，以及此前 7 天内最多 100 条背景；每条最多 2,000 字符，模型每会话最多输出 30 条事项。超出输入上限必须提示不完整。
- 图片、语音、附件不解析，不打开链接。有链接的业务信息不能因文字少忽略；仅凭不可读附件不定级，可读文字已明确证明风险时保留等级并标资料不全。
- 复用现有 OpenAI Responses 接口（`store: false`）、严格结构化输出、数据库任务与租约。服务端复核用户、handle、引用和工作日条件；聊天内容不是可执行指令。
- 模型输入和结果展示均检查有效正文授权、可见且允许同步的会话、当前授权下的逐条观察及未删除消息。`@` 按该消息的明确身份元数据解析，不凭名字猜对象或扩大归属。
- 正文和派生总结分别加密；密钥、正文、完整 prompt 不进日志或审计。查看留最小审计，浏览器不持久化聊天副本，也不直接调用 OpenAI。
- 关闭、替换任务、撤权或输入变化后，旧调用不能继续提交过时结果；已有结果也须通过当前权限和资料校验才能显示。

验收先看四件事：有没有漏掉 P0/P1、把运营信息当闲聊、把不同事项合错，或把“已回应”写成“已解决”。没有结果不代表没有风险。

## 上班、下班与最近七天（2026-09-15）

`/dashboard/offhours-summary` 支持选择 CM、日期和时段，刷新保留当前选择。采用 `Europe/London` 当地时间并随夏令时切换：上班为所选日 10:00–18:00，下班为所选日 18:00–次日10:00。查询采用左闭右开边界，18:00 和 10:00 的消息不会在相邻时段重复。可选日期为英国今天及前六天；下班时段归于开始日期。

仅使用当前正式入库的 CAP 达人，按人员合并 handle，并检查所有相关群聊和私聊。普通 CM 看自己的总结；系统主人及达人完整管理权限持有人可切换 CM，已有 Remi 试读权限仍仅适用于 Remi。每次读取和调用 AI 前仍复核当前授权、名单和消息材料。消息内容页的单独 CM 限制不变。

后台按 CM、日期、时段保存独立任务，唯一约束保证同一时段不重复创建；切换历史日期是只读，不触发同步请求或覆盖别的时段。已有 AI 配置启用且周期调度开启时，后台每十五分钟补建最近七天已开始的时段，时段内每十分钟检查新材料，结束后每小时检查至刷新期限（结束后至少24小时；首次历史补算自创建起24小时）。无内容不调用 AI。旧手动报告保留，不混入固定时段历史。

进行中的时段标为部分结果；未准备、AI排队、同步滞后、材料截断和不可读附件分别提示。保留 P0–P3 分级、最新进展和对应原文，不自动发送回复。不承诺尚未同步的历史记录已覆盖。
