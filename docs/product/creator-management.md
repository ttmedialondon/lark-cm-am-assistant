# 人员身份与我的达人

更新：2026-09-11。第一步认清人员身份；第二步单独判断达人由谁负责。旧三阶段工程不恢复，分类为“达人”不自动归给某位 CM。

## 现在先做：把所有人认清楚

入口是后台 **人员目录**（`/admin/contacts`），不是前台达人名单。

```text
全部在库人员
    ↓ 按同一个联系人去重，不按 CM 重复扫描
从本人可读取的历史发言中挑选重要片段
    ↓ OpenAI 判断一个主要身份
六类之一 ／ 待识别
```

| 类别 | 主要看本人说了什么 |
|---|---|
| 达人 | 本人实际做直播、短视频、带货或内容合作；替别人协调不算本人是达人 |
| 其他机构负责人 | 代表其他机构管理、对接或安排达人；不把所有服务商都算机构负责人 |
| 同事 | 明确为本公司工作；已核实的内部租户事实可以直接保留，不重复付费猜测 |
| 商家 | 代表品牌、店铺或商品供应方开展业务 |
| 字节官方 | 明确代表字节／TikTok 官方处理业务；只是讨论 TikTok 不算官方人员 |
| 其他人员 | 有足够材料确认其身份不属于以上类别；不是信息不足的兜底 |

只允许一个主要类别。低于 **0.95**、证据冲突或信息不足，统一 **待识别**。没有可读发言、只有寒暄或无法提取文字，也显示待识别及原因，不发送空材料给 API。阈值是保守的产品门槛，不是保证 95% 准确；结构化输出仍可能出错。[OpenAI Docs](https://developers.openai.com/api/docs/guides/structured-outputs)。

历史不限定最近多少天；本人重要发言和分散时间的片段结合选取。业务词只帮助找材料，不直接决定类别。昵称、handle、群名不能代替本人业务证据；不需要先找到 CM 对话，也不要求 handle 齐全。不会把同群其他人的整段聊天传给模型。

执行复用现有 OpenAI 配置及队列：每人最多 **16 条本人片段、8,000 正文字符**，全局最多 **3 路并行**，每个任务最多 **2 次尝试**。尝试计数包含领取后检查，不等于付费调用次数。同一规则版本自动处理每人一次，刷新页面不重发请求；新入库人员在开关启用时补入队列，异常明确留在目录，不无限循环。

保存并开启“全员身份识别”后开始；关闭保留排队任务，停止新领取并取消在途任务，迟到结果不再写入。重新开启会继续排队任务；被取消或需要补材料的人可由主人在详情点“继续识别”，沿用剩余尝试，不清零预算。密钥留空不覆盖已有密钥。

人工已确认身份优先，其次是已核实内部同事，最后才是新 AI 分类。重判只替换旧 AI 分类，不覆盖人工、租户原始事实、权限、账号或 CM 归属。旧 AI 结果保留为历史记录，不当作本轮结论。发送前和保存前都检查授权、作者和原文是否仍有效；正文不进普通日志。

目录保留类别、姓名搜索、识别进度和人员列表；开启／关闭和人工确认仍由系统主人操作，不扩大聊天权限。

## 第二步：达人归属判断

临时入口在后台 **AI 功能 → 达人归属判断**（`/admin/ai/creator-ownership`）。

**选 CM → 预筛选 → 点击开始分析 → 看结果 → 人工确认关联。**

默认 Remi（Quanzhen Liang），也能选择其他有效正文授权的负责人。始终用稳定用户 ID 关联，不按姓名猜测。只取人员目录当前有效分类为“达人”、有 Lark 用户且没有有效负责人的人；已有的人级归属或旧账号名单仍有负责人时都排除。结束的历史关系不阻止扫描。一人多个 handle 也只判断一次。

### 先在本地筛选，不调用 AI

| 材料情况 | 处理 |
|---|---|
| 所选 CM 没有可读材料 | 暂不分析：无可读材料 |
| 只是同群，没有直接交流线索 | 暂不分析：未找到直接交流 |
| 只有问好、表情、感谢、系统消息或广播 | 暂不分析：缺少业务内容 |
| 只有单方业务发言，没有回应或明确负责说明 | 暂不分析：双方材料不足 |
| 相同人、CM、规则、模型和材料已经成功分析 | 复用结果，不重复请求 |
| 完整有效对话本身超过材料上限 | 暂不分析，不裁掉可能改变意思的句子 |

普通情况至少双方各一条实质消息并涉及业务，不硬设“必须十条”。少量消息明确说明接手、负责或交接时可送 AI 核实。暂不分析不等于不属于该 CM；预筛选规则要抽样检查是否漏人。

### 每次只看一位达人与一位 CM

只读取所选 CM 当前有效授权观察到的材料，不复用第一步跨 CM 汇集发言的取材范围。结合相关私聊、群内双方回复/@和必要上下文，单纯同群、时间相近不算实际业务往返。没有回复标记的连续群聊，只在双方有具体共同话题及回应线索时作为弱材料。

历史不限最近多少天。兼顾最早、最新以及交接、代班、终止合作等反向材料。每对人最多 **6 段、40 条消息、16,000 个正文字符**；保留完整交流，不把整个 CM 的消息上传。如果反向段无法完整装入，整个人暂不分析，不能只保留旧正向材料。缺失历史、媒体文字或对话关系时不得猜测。

### AI 的三个结果

| 结果 | 规则 |
|---|---|
| 建议关联 | 有持续实际对接或明确负责说明；至少 0.95，引用有效，没有未解决的冲突或缺项 |
| 待确认 | 有业务合作，但不足以确认当前负责关系；没有材料不能当反向证据 |
| 不建议关联 | 有明确反向证据，例如交接、临时帮忙或已经结束；不能顺手归给其他 CM |

一次样品处理、有私聊、回复多、群名、handle 或 CAP 身份都不能单独证明负责人。高可信的“持续对接”至少引用两个跨日双向业务回合；“明确负责”须实际引用该 CM 对这个达人的负责说明，不能借用材料中另一条未引用消息。反向结论也要有真正反向原句支撑。旧合作不自动失效，但也不自动证明当前仍由该 CM 负责。0.95 是产品门槛，不是准确率承诺。

“负责”指实际业务对接，不要求合同、正式任命或“我是你负责人”原话。要分清 CM 临时帮助别人，和 CM 自己休假让同事短时代班；若原 CM 后来继续对接，不能只凭已结束的代班认定交接。退出机构/CAP 也不等于停止非 CAP 业务合作。抽样限制、关键词标记只是选材提示，不是已发生交接的证据，不能凭提示编造冲突。结论置信度表示对本条判断的把握，不是归属概率。

模型返回固定结论、分数、简短说明、引用、冲突和缺项；使用现有 Responses 接口的严格结构化输出，服务器核验引用与业务门槛，不把格式正确当作事实正确。[OpenAI 官方文档](https://developers.openai.com/api/docs/guides/structured-outputs)

### 确认与运行

- 仅主人可预筛选、开始、暂停、继续和单条/批量确认或暂缓；获准查看 AI 页面者只读，原文证据仅主人可看。不恢复旧测试编辑特权。
- AI 不直接修改负责人。主人确认“建议关联”或“待确认”结果后，写入独立的人级正式归属；handle/CAP 可缺，不写旧账号名单，也不触发消息总结。已有负责人不可抢占。
- 先分析约 20 人，优先覆盖私聊、群聊、少消息和交接；核对后再点“分析剩余”。没有可用样本的类别不伪造覆盖。
- 预筛选由一个后台线程处理，不阻塞聊天同步，也不占 OpenAI 槽。付费分析与现有 AI 功能共用最多 **3 路**。
- 开始按钮只校验引用并排队，完整历史复核在后台发送 API 前执行，避免批量点击长时间卡住。预筛选进度、判断结果和实际请求数分别显示。
- 每人通常一次请求；明确可重试的限流最多再试一次。网络结果不明或进程中断，不自动重发可能已付费的请求。
- 刷新只读状态。暂停后不登记新请求，已经开始的少量请求允许收尾；暂停不会撤销已消耗的用量。
- 判断规则升级后另建批次，旧结果保留供历史查看，不能直接确认或混用缓存。
- 发送前、结果保存前、确认前检查人员、负责人、授权和原文。引用被冻结且绑定所选 CM；新增相关对话、交接、编辑或撤权会让旧材料失效，无关会话不影响。
- 页面分别显示待分析、排队、分析中、完成、跳过、异常，以及已发起请求和 token 用量；本地处理人数不能冒充 API 调用数。
- 列表轮询分页并只核验所引用消息的当前阅读权限与内容，不重扫全部历史；完整历史是否有新进展，在打开原文、发送、保存和确认时检查。列表中的历史 AI 建议不保证当前仍可确认。

这一步不做自动账号检索、Excel/CAP 重构、协作 CM、多负责人、自动交接、消息回复或总结。之后统一界面时再接，不能重新启用旧流程代替。
