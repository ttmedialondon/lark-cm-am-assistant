# 达人名单：先认清人，资料齐了再入库

2026-09-11 新需求设计。**本次清空旧达人数据并停用扫描；下文的新入库门槛、补查与页面分区尚待开发，不代表已经上线。**旧代码仍允许人工确认缺 handle 的记录，不能直接重新启用旧流程。历史“handle 可以后补入库”的要求以本文为准作废。

## 一句话理解

**AI 说清楚“是达人、是我负责的”，并且对应 Lark 用户和 handle 都核对好了，才能进入“我的达人”。CAP 可以为空。**

```text
Excel / 已同步的相关历史对话
             ↓
锁定 Lark 用户，选出他和 CM 的少量业务对话
             ↓
OpenAI：是达人？是这个 CM 负责？能核实哪个 handle？
             ↓
三项齐全、判断通过、没有冲突 → 我的达人
缺资料 / 判断不清楚         → 待处理，补齐后再检查
明确不是达人 / 不归我负责   → 不纳入
接口失败 / 引用校验失败     → 未完成，不算达人也不算否定
```

建议全部通过后自动入库，只有缺项或不确定的交给 CM；是否仍加一次 CM 点击确认，等待本次选择。无论选哪种，人工点击都不能绕过门槛。

## 三个条件怎么检查？

| 条件 | 什么才算满足 |
|---|---|
| 是达人 | OpenAI 根据本人实际业务对话判断通过，有可核验原文，不是仅凭 handle、昵称或关键词 |
| 是我的达人 | OpenAI 确认这个 CM 在实际安排或跟进此人的达人业务，不是偶尔帮忙或只在同一个群 |
| 信息完整 | 选定稳定的 Lark 用户，并核实一个属于他的准确 handle；不能只填姓名或猜一个账号 |

前两项分别保存“通过 / 不通过 / 信息不足”，不用一个总分代替。通过还需服务器核实消息作者、授权和引用；任何用户、账号或负责人冲突先待处理。CAP / 非 CAP 不明显示 `—`，不阻止入库。即使资料齐全，AI 证据仍不足，也不能只靠 CM 点确认进入正式名单。

## AI 凭什么判断？

- 本人谈自己的 LIVE、视频、样品、商品推广或创作者合作；CM 对这些业务有实际回应、安排或跟进。
- 私聊必须核实真实对端；群聊必须有两人的明确回复或真实 @ 关系。仅同群、都有发言、昵称相似、发过链接、聊过几句，都不够。
- 服务器检查原消息、作者、当前授权和双向业务关系。聊天内容只是证据，里面的指令不会当系统命令执行。
- 建议先沿用两项评分都至少 **0.95** 的保守阈值，再加明确通过、直接证据有效及无冲突检查；高分不能抵消缺项，也不能代替原文。上线前用小批真实样本核对效果。
- handle 只辅助判断业务身份，不是“是达人、是我的”的决定证据；但准确的账号关联是正式入库的必填资料，两件事分开看。

分数不是保证 95% 正确。结构化输出仍可能判断错误，因此保留服务端原文校验和纠错入口。[OpenAI Docs](https://developers.openai.com/api/docs/guides/structured-outputs)。不因后续扫描就静默换人、换 CM。

## handle 怎么找？

1. **先找现成的。** 服务器提取 Excel 中的账号、此用户历史消息中的自报账号和 TikTok 主页链接。群名与转发的视频可以帮助检索，但不是账号归属结论。
2. **让 OpenAI 核对归谁。** 给它准确账号及相关少量原文，要求返回账号、消息引用和“属于此用户 / 不属于 / 不确定”。只有本人明确自报自己的账号且精确文本可验证，才自动绑定；分享别人的视频、昵称相似或群名命中均不够。
3. **找不到就让 CM 补。** 显示 `—`，CM 输入 handle / 主页链接，并明确确认它对应所选 Lark 用户。校验格式、重复账号和归属冲突后，可作为人工核实的账号资料；这不等于替 AI 通过前两项判断。
4. **不编、不强配。** AI 只能提取和判断实际提供的资料，不能凭模型记忆猜用户名。一个人有多个 handle，逐个核实，先选一个主账号；不能认领一个就连带挂上所有账号。历史改名或账号冲突先交 CM。

本地提取保留精确 handle / URL，脱敏不能把与显示姓名相同的账号一起抹掉。只规范 `@`、首尾空格及平台规则允许的大小写；不删除账号内部符号来制造“精确匹配”。系统只保证所提供证据下的关联，未验证的当前账号有效性不能宣称已经验证。

## Excel 怎么处理？

1. CM 上传自己的 CAP 名单，最少一列 `handle`；上传者就是负责人。主人代导入时先选 CM。
2. 支持 handle、`@handle`、TikTok 主页链接，统一首尾空格和大小写。视频链接、短链、姓名不是 handle；不靠相似昵称自动认人。
3. 相同平台、相同 handle 无冲突时合并来源；相似账号只给建议，不自动合并。Lark 稳定 ID、已有精确账号关联或 AI 本人账号证据可以帮助找到对应用户；找不准就显示 `—`，等 CM 在自己的可选用户中搜索。
4. Excel 说明“这是我的 CAP 名单”，但不能单凭一行 handle 猜出 Lark 用户，**也不能跳过这次规定的两项 AI 判断直接入库**。CM / TAP CM 列若与上传范围冲突，预检报错，不擅自转给别的 CM。
5. 先预检再提交；重复上传不重复建档，不导入无关隐私列。

CAP 是签约达人；非 CAP 是未签约但有推品合作的达人。没有出现在 Excel 不等于非 CAP，类型不明一直保留 `—`，等明确证据或 CM 补充。

## 怎么少发消息，又不只看最近？

1. **先在服务器找人。** 检索当前授权内已同步的历史，不限近 30 / 90 天；按稳定 Lark 用户合并群聊、私聊线索，排除已知内部同事和机器人。业务词只用于找片段，不用于认定达人。
2. **只选两人的相关对话。** 私聊要确有双向沟通；群聊优先取明确回复、引用或真实 @ 对话，不把其他成员的聊天打包发送。没有 @ 不代表一定无关，但只能作为本地待核对线索。
3. **先给发送预览。** 每人最多 3 组对话、30 条消息，整个人的模型输入包最多 16,000 字符，每条最多 1,500 字符。姓名用代号代替，尽量遮盖电话、邮箱等无关个人信息；不能保证自由文本已经完全匿名。
4. **明确启动才调用 AI。** 首批最多 30 人，后台全系统共享 3 个 AI 并发槽。第一次一起判断身份、负责人和现有账号线索；确有新线索时最多一次定向补查。每人最多 2 次请求，补查和失败重试共用这两个名额，整批最多 60 次，不是重试后再额外加两次。数据库保存重试复用结果、不另付一次模型调用。信息不足交 CM，不自动扩大到全部聊天。
5. **按人数看进度。** 显示准备、排队、核对中、结果、未完成及预算，可取消准备或暂停。继续只处理本批剩余预算内的未完成者，不重跑成功结果、不清零次数。刷新只查状态，不触发新分析，不覆盖正在编辑的名单。暂停停止新任务并拒收失效任务结果；已经发出的 HTTP 请求无法撤回。

已确认的人不反复扫描，相同有效证据的成功结果不重复付费。下次有新相关证据再明确准备；失败、没选入首批和本地线索不足，都不等于“不是达人”。AI 任务必须有具体 Lark 用户；不能创建用户和 handle 都没有的空白达人记录。

新 CM 授权后只等待本地历史同步就绪，不再自动上传历史。旧全量消息段扫描与重试入口停用，不能恢复旧队列。不做图片识别、附件原件读取，不声称尚未同步的历史已经核对。

OpenAI 请求继续使用结构化输出和 `store=false`；这不等于服务商零保留，具体数据控制见 [OpenAI 数据说明](https://developers.openai.com/api/docs/guides/your-data)。

## CM 怎么核对、怎么补？

入口仍用 `/dashboard/creators`，不另建后台页面。表格保留 **handle｜对应用户｜来源｜CAP 类型｜状态｜操作**；来源只有 AI / Excel，可同时存在。缺项显示 `—`，不恢复“查看依据”按钮。

- **我的达人**：只计三项全通过的正式记录。
- **待处理**：说明“缺 handle”“缺用户”“达人身份待核对”“负责人待核对”或“账号有冲突”。缺用户点击搜索自己有权选择的用户；缺 handle 点击填写。资料完整而 AI 不确定的，补业务线索后再有限核对。
- **本批扫描**：单独显示检查人数、通过、不纳入和未完成，不把这些数字加到达人总数。`我的达人 40` 不再混成“全部 100”。

更换 Lark 用户或 CM，旧两项 AI 判断失效，必须重新核对；只改 handle，则重新核实账号关系，仍有效的同人、同 CM 判断可复用。改动破坏入库条件时先退出正式名单，不能让旧归属继续生效。CAP 修改不触发无关重扫。批量处理也逐条检查，不能绕过规则。
