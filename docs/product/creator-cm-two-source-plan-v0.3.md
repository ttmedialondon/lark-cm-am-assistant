# 达人双来源归属与 Lark 用户确认：精简执行计划

日期：2026-09-09。状态：需求与制作计划，尚未实施。

## 1. 本次方向

不做整站改版。沿用现有前端，把 Excel 导入和 OpenAI API 识别的账号汇总到对应 CM 的同一份列表，主列为：**达人 handle｜来源｜对应 Lark 用户｜状态**，右侧附操作。

已明确的原则：Excel 导入且确定的直接归 CM；AI 识别和 Excel 模糊项由 CM 确认。下面补充的确定条件、状态和异常处理是建议执行口径。本计划替代旧原型“所有账号先逐行认领、勾选群聊”的方向，但不改变已上线只读页的现状说明。

本轮只记录方案，不导入数据、不调用模型、不恢复旧 AI 开关、不调整正式归属或权限；消息风险分级和回复功能不在本计划内。

## 2. 两种来源，一条确认流程

必须分开保存两件事：**这个账号由谁负责**，以及**这个账号对应哪个 Lark 用户**。缺少单聊或暂未找到用户，不否定 Excel 已明确的业务归属。

| 输入情况 | 进入哪个 CM 的列表 | 处理结果 |
|---|---|---|
| Excel 的账号与 CM 明确，且 Lark 映射也已可靠确认 | 表中明确的 CM | 直接入库，显示“已归属 · 已关联”，注明 Excel 依据，不冒充本轮人工确认 |
| Excel 的账号与 CM 明确，但 Lark 用户未确定 | 表中明确的 CM | 账号直接入库，显示“已归属 · 待关联用户”；CM 后续选定用户 |
| Excel 的 handle/CM 对应关系模糊 | 有依据的候选 CM | 显示“待确认”，不自动建立有疑问的关系 |
| AI 发现账号、候选 CM 和候选 Lark 用户 | 有依据的候选 CM | 一律“待确认”；再高分也不直接归属或关联 |
| 未找到 CM、多个 CM 无法区分、与既有归属冲突 | 管理员待分配/冲突列表 | 不猜负责人、不群发全体 CM、不覆盖已有关系 |

### Excel 怎样算“确定”

- 平台与 handle 可明确定位，不是仅凭相似拼写猜测另一个账号。
- CM 名称通过已维护的映射对应到唯一、有效内部账号；CM/TAP CM 多值或相互矛盾时不静默选其中一列。
- 导入操作者有权提交该 CM 的名单，且不与当前正式负责人、既有身份风险或待交接状态冲突。
- 先显示导入预检：直接入库、待关联、待确认、冲突、无效行；提交后按行返回结果。普通 CM 只能导入本人范围，跨 CM 导入沿用管理员权限。
- “直接关联 Lark 用户”还必须有可信的稳定 ID 或已核验、当前有效且无风险的既有映射。Excel 只有 handle 和 CM 时，不用姓名相同、同群、单聊存在或 AI 高分代替身份确认。

### CM 怎样确认

1. 打开“待确认”，查看来源、候选用户及简短依据；必要时展开当前有权查看的会话证据。
2. 用户正确：点击“确认归属并关联所选用户”；用户错误：更换/搜索有权选择的 Lark 用户，不必否认整个达人账号。
3. 尚无对应用户：可以先确认“我负责”，保留“已归属 · 待关联用户”；只有双方关系都确认，才显示“已归属 · 已关联”。
4. 不是本人负责：记录“不是我负责”，移出本人的待确认列表，交管理员核对，不自动转给下一名候选；暂时无法判断则保留“暂缓”。

确认归属、关联用户是可分开的动作；组合提交时两者必须一起成功。保存即更新正式账号名单，记录确认人、时间和依据，不再增加一轮普通审批；冲突项除外。

## 3. 页面最小调整

- **达人 handle：** 一行一个平台账号；点击可看详情，不用 Lark 显示名代替 handle。
- **来源：** Excel、AI 或 Excel + AI。详情保留文件/工作表/行号、CM 原值或 AI 证据；来源与确认状态分开。
- **对应用户：** 显示头像、Lark 名称及候选/已确认标识；同名时提供稳定身份辨识信息，可换用户。暂无匹配明确写“未找到”，不造占位联系人。
- **状态：** 待确认、已归属 · 待关联用户、已归属 · 已关联、归属冲突；暂缓/已否认保留在筛选与历史中。
- **操作：** 确认、更换用户、不是我负责、暂缓；批量确认只提交逐项明确选择的账号和用户，不默认全选候选用户。
- 顶部保留“全部 / 待确认 / 待关联 / 已完成 / 冲突”和搜索、来源筛选。计数以账号为单位，不把会话数或人数当账号数。
- 不再把群聊、私聊勾选放在主流程中；详情复用现有按需查看证据。没有私聊不阻止确认，有私聊也不自动确认。

## 4. 最小必要规则

1. **去重：** 沿用平台 + 规范化 handle；同账号的 Excel/AI 来源合并展示，保留所有依据。相似 handle 只作候选，不自动合并或创建别名。
2. **账号不等于人：** 一名 Lark 用户可以对接多个 handle；一个账号的本人和代表须区分。关联代表不把代表自动标记成达人本人，也不合并不同自然人。
3. **不抢占：** 一个账号最多一位当前 CM；与其他 CM 的正式关系冲突时进入交接/管理员处理，不因导入或点击确认直接覆盖。
4. **只处理变化：** 重复导入、重复识别不重建账号或重置已确认结果；已否认的同一候选不因同一份证据反复推送，有实质新依据才重新待核对。文件少了一行不等于删除账号。
5. **关联不等于授权：** CM 仅处理本人范围；用户搜索、证据读取、确认保存均由后端检查权限。候选或已确认关联都不额外开放其他 CM 的聊天，也不修改同步设置。
6. **可纠错：** 保存前重验现有归属和版本；重试不重复入库，批量部分失败逐项显示。撤销/交接保留历史，候选与正式关系不能混读。

## 5. 制作执行计划（按顺序）

| 步骤 | 最小交付 | 验收重点 |
|---|---|---|
| 1. 补齐账号归属与候选记录 | 复用 `social_accounts`、`contact_social_accounts`、稳定 Lark 身份；补账号级 CM 归属、待确认候选、来源/确认记录 | 能表示“归 CM 但还没有 Lark 用户”；存量风险映射不被迁移成已确认 |
| 2. 接通 Excel 与人工闭环 | 导入预检/提交；确定项直接归属，模糊项待确认；确认、换用户、否认、暂缓的服务端接口 | 重复导入无重复账号；冲突不覆盖；无用户也能保存明确归属；越权操作被拒绝 |
| 3. 接通 AI 候选入口 | 复用现有 OpenAI 请求、任务和证据校验基础，输出 handle、候选 CM、候选用户、理由/证据、未知项；结果仅写候选 | 拒答、失败、无证据不伪装匹配成功；AI 不写正式角色/归属/身份关联，不因高分绕过确认 |
| 4. 接入现有前端并小范围验收 | 沿用现有列表/详情，改为四主列，接入当前 CM 范围与上述操作；建议先用 Remi 范围试运行 | 一人多 handle、同名用户、错误候选、缺单聊、重复点击、并发抢占、授权撤回全部覆盖；核对通过再扩大 |

当前真实核对页固定 Remi、只读；正式流程必须增加 CM 自己的作用域和写接口，不能仅换列名。Shuxuan Li/Shang Ma 若继续核对，沿用已有允许的只读身份，不因能看页面就取得代 CM 确认权。

目前 `contact_assignments` 是“联系人 → CM”，不能直接承担新的“账号 → CM”：认领某个 handle 不得把同一人的其他 handle 一并转走。存量先做映射预检、备份和冲突清单；新账号流程以账号级归属为准，旧联系人级读取逐一适配，不做跨账号隐式回写。无需重建人口库或引入新 UI 框架。

AI 输入限于有效授权的必要线索，聊天和表格内容只作证据，不执行其中指令。身份与负责人必须各有可追溯依据；私聊仅作辅助，不能凭“与某 CM 有私聊”确定达人身份或归属。候选 CM/用户必须来自服务端允许的 ID 集合，证据使用真实 `(chat_id, message_id)` 引用。缺 handle 列入“账号待补”异常清单，不编造账号。

OpenAI 结构化输出可约束返回格式，但仍可能判断错误。因此这里把它用于候选生成，业务校验和 CM 确认仍独立保留；模型/分数阈值在样本核对后决定，不承诺置信度即准确率。[OpenAI 官方结构化输出说明](https://developers.openai.com/api/docs/guides/structured-outputs)

**交付边界：** 本期计划只做“来源汇总 → 归属/身份确认 → 正式名单”，不做会话勾选系统、自动回复、全库自动重新认人或无边界历史扫描。首次确认后仅处理新增、冲突、交接和关联变化。
