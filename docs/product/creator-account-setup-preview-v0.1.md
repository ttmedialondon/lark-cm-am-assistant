# 达人账号首次确认与增量维护：预览需求 v0.1

日期：2026-09-08。状态：假数据原型与后续业务需求，不是正式入库功能的完成说明。

## 1. 业务目标

让负责人第一次集中核对“哪些达人账号由我负责”，再按需补充联系人及相关会话。首次核对后，只处理新增账号、职责变更和新增关联，不要求重复确认整份存量名单。

页面以账号为主，不以人口库联系人或聊天群为主。账号可以先成为正式业务记录，再逐步补全联系人与会话。账号的业务负责关系、自然人身份和聊天访问权限分别处理。

本次交付只用于确认流程与界面效果。旧的 115 位正式达人及既有 143 项整理台账保持不变，不从中抽取真实资料装饰原型，也不据原型操作回写正式数据。

`sessionStorage` 不是跨设备、跨浏览器的正式保存，也不保证浏览器恢复标签页后一定清空。没有存储权限或内容损坏时，页面应继续可用并说明演示状态未保存。恢复缓存时只接受当前版本及预置假数据中的合法标识，不把浏览器存储视为可信业务输入。

以下章节区分“原型应表达的交互”与“正式版本的后续要求”。事务、幂等、正式审计和真实增量流转均不属于本次已实现能力。

## 3. 核心对象与关系

| 对象 | 代表什么 | 不代表什么 |
|---|---|---|
| 达人账号 | 一个业务管理的社媒账号，保留平台、handle、来源与确认状态 | 不等于人口库中的某一个自然人，也不等于一个群 |
| 自然人／联系人 | 系统里的具体对接身份，可与账号建立有依据的联系 | 不是看到相似名称就确认的账号所有者 |
| 业务负责人 | 当前负责跟进该账号的内部人员 | 不等于账号所有者，也不自动获得全部聊天访问权限 |
| 会话 | 群聊或单聊；与账号建立业务相关关系 | 同群不证明同一自然人，勾选也不等于授权或启动同步 |
| 消息 | 某个会话中的已授权、已同步记录 | 不独立定义达人身份或负责关系，不能因关联账号而扩大读取范围 |
| 来源记录 | Excel 的文件、工作表、行号、CM／TAP CM 原值，或人工添加记录 | 不等于账号和联系人已经正确匹配，更不是匹配准确度分数 |

关系要求：

- 一个账号可以关联零个、一个或多个联系人。家庭、团队或共同运营账号不能强制合并为一个自然人。
- 一个联系人可以对接多个账号；保存的是各账号的对接关系，不自动断言账号归该自然人所有。
- 一个账号可以关联零个或多个会话；同一会话也可能同时服务多个账号。单聊不是必填项。
- 一个账号最多有一位当前业务负责人，可以暂时未分配。历史交接要保留，不能把多名源表 CM 静默压成最后写入者。
- 消息仍归属于原会话；不因一个会话关联多个账号就复制正文或重复统计成多份原始消息。

这些是业务关系，不要求本次建立新表。正式版本应先核对已有账号及关联结构能否复用，再作最小必要迁移；不得直接把现有“按联系人分配负责人”的语义套成“按账号分配负责人”。

## 4. 页面与操作逻辑

### 4.1 首次集中核对

页面先说明两项不同的工作：“确认负责的账号”和“补充相关联系人／会话”。主列表每行显示一个账号，至少包括 handle、来源、负责确认状态、联系人与会话补充状态。

负责人逐行选择“我负责”“不是我负责”或“暂缓”。行级负责选择与展开区的会话复选框在视觉、标签及状态上都分开。

- “我负责”：确认本人的业务职责，不自动确认候选联系人，也不自动勾选群聊或单聊。
- “不是我负责”：记录对本次分配候选的否认；不能自行删账号、结束另一人的现有职责，或把账号交给任意他人。
- “暂缓”：保留在待处理范围，不能计为已确认或被批量保存顺带确认。本次只演示暂缓状态；填写原因留待正式版本。
- 没有明确选择的行保持未处理。批量演示保存只处理明确选定的行，不隐含全选剩余账号。

首次核对可以分次完成。界面应区分“本次保存完成”和“全部账号已处理”；仍有未处理或暂缓项时不得显示全量完成。

### 4.2 展开账号查看关联

展开区展示来源摘要、联系人候选和相关会话。来源与匹配线索分栏表达，不能把“来自 Excel”显示为“身份已准确匹配”。

会话列表支持多选。每项显示群聊／单聊类型及简短相关线索，允许查看虚构的消息示例，以演示用户如何自主判断。列表中的候选关联不能仅因系统推荐就默认成为正式关系。

- 勾选含义是“将此会话关联到该账号的业务工作范围”，不是“为谁开通查看权限”。不得使用会扩大权限理解的文案。
- 取消勾选只表示不将该会话纳入本次账号关联，不删除聊天、不退出群、不撤销其他账号的关联，也不关闭同步。
- 账号负责选择不受会话勾选影响；会话选中数量也不得充当“已确认账号数”。
- 缺少联系人、缺少会话或只有群聊，都不阻塞账号层面的负责确认。界面显示“联系人待补”“会话待补”，而不是“不能入库”。
- 有多个联系人或同一会话含多个账号时，保留多对多的事实与待确认项，不强制挑出唯一自然人。

### 4.3 来源与手动补充

Excel 导入和人工添加都可以提供账号线索。原型用预置的人工来源条目表达手动补充，不要求本次增加真实上传或新建表单；演示账号同样必须使用 `demo_` 前缀。

正式版本的来源要求：

- Excel 保留文件指纹、工作表、所有有效源行、原始 handle、CM／TAP CM 原值。相同账号的重复行合并展示但不丢来源。
- 源表明确列出负责人，只能作为职责来源。CM 与 TAP CM 的业务含义分别保留；多人标签或不能对应内部账号时，显示待确认，不自动选一人。
- 人工来源记录添加人、时间和必要说明，不能伪造 Excel 行号，也不能跳过冲突与权限校验。
- 相似 handle、群名、姓名和单聊只作为待核对线索。需要区分“原文相同”“明确别名”“相似候选”，不把相似度阈值直接当作确认。
- 缺人口库联系人时，不凭 handle 创建虚假的自然人占位记录。账号本身可先保存，联系人后补。

### 4.4 首次完成后的增量

正式版本中，已确认、没有变化的存量账号留在“已确认”视图，不重新推入首次核对队列。

| 变化 | 应处理的增量 | 不应发生的动作 |
|---|---|---|
| 新账号进入名单 | 新增该账号的负责确认待办 | 重置全部存量确认 |
| 已有账号新增来源行 | 补来源；有职责矛盾才建立冲突待办 | 重复建账号或静默变更负责人 |
| 出现新联系人或新会话线索 | 给该账号新增关联待核对提示 | 自动勾选关联或推翻已确认职责 |
| 账号 handle 变更或新增别名 | 复核平台身份与别名关系，保留历史 | 仅凭相似名称自动合并两账号 |
| 负责人调整 | 进入有权限的明确交接流程 | 新负责人点击“我负责”抢占现有关系 |
| 账号停用、源表 Unlink 或被移出某次表格 | 作为变更线索等待处理，保留来源和历史 | 因单次导入缺失直接删除账号或历史 |
| 聊天授权失效或访问范围收缩 | 立即限制读取，并提示相关会话当前不可读 | 因历史勾选继续提供正文 |

## 5. 权限与安全边界

本次只开放指定用户的假数据预览。有效 owner 也不是读取未授权聊天的理由；本次没有需要读取真实聊天的业务操作。

正式版本必须在两个层面分别判定：

1. 是否能确认或调整这个账号的业务负责关系。
2. 是否能在当前授权、同意及同步范围内查看这个会话／消息。

前端复选状态不能替代任何服务端授权。会话关联后的可见范围仍是“业务相关范围”和“当前有效读取权限”的交集。业务关联既不能新增授权，也不能放宽现有群成员、身份、来源同意或消息观察范围等约束。

账号／会话业务关联必须有自己的语义，不得复用 `authorization_chats.sync_enabled` 存储。同步配置管理是否采集，业务关联管理如何组织，两者互不替代。页面也不向其他人授予后台页面权限。

正式读消息时重新检查授权，避免“打开页面时有权限，随后撤销后仍可继续读”的情况。客户端提交非候选、越权或已失效的联系人／会话标识必须被拒绝；不能先查全库再只在前端隐藏。

## 6. 正式版本后续实现契约

本节不是本次原型的后端实现范围。

### 6.1 事务与冲突

- 账号确认、联系人关联和会话关联是可分别完成的业务动作；联系人／会话为空是合法状态，不得用数据库非空约束使其反向阻塞账号。
- 单个动作涉及的账号记录、当前负责关系、来源及审计在同一事务内提交。若提供“确认并保存关联”的组合动作，则整项原子提交；任何非法关联都应明确失败，不静默丢弃用户选择。
- 批量提交逐项返回成功、冲突或失败。失败项保持未完成，可单独重试，不显示整批全部成功。
- 保存前在服务端复核当前用户权限、目标记录版本和当前负责人；对同一账号的并发更新进行锁定或等效并发控制。
- 数据库保证一个账号最多一条当前负责关系。已有其他负责人时显示冲突并转交接流程，不自动结束旧关联，不依赖最后写入覆盖。
- 账号的稳定标识与可变 handle 分开。账号去重使用经校验的平台键及规范化标识；允许保留标点差异，不用宽松模糊归一化合并不同账号。

### 6.2 幂等与重试

- 每个正式写动作携带幂等键，服务端按操作人、操作类型与键约束唯一，并记录请求内容摘要。
- 相同键、相同内容重复提交，返回此前结果，不重复创建账号、关联或业务审计。相同键、不同内容明确拒绝。
- 网络超时不能被视为未提交；客户端以原幂等键重试或查询结果。用户改动了选择后使用新动作，不覆盖不确定的旧动作。
- 乐观版本冲突不自动合并身份或负责关系；界面展示最新状态并要求针对冲突项重新处理。

### 6.3 审计与变更

正式审计至少记录操作人、时间、账号稳定标识、动作、变更前后状态、来源引用、理由、版本及请求幂等标识。身份关联与职责关联分别记录，不能用一份含糊的“已确认”覆盖多个含义。

审计不得保存不必要的聊天正文、联系方式或凭据。相关聊天证据引用与业务决定分开；读取真实正文仍遵循现有阅读审计与有效权限检查。浏览器演示保存不写入正式业务审计。

纠错采用可追溯变更，不删除原始导入或旧决定。改负责人必须有明确的新旧负责人、交接时间和操作权限；取消本人候选负责不等于撤销别人的当前职责。已有 115 位达人及 143 项台账迁移到账号模型前，必须另做映射预检、备份、冲突报告和迁移验收，不能由此次预览顺带执行。

## 7. 验收矩阵

“原型”用于本轮演示验收；“正式”是后续上线前必须满足的业务验收，不能以假数据交互替代后端测试。

| 范围 | 场景 | 预期结果 |
|---|---|---|
| 原型 | 指定 UUID、active、有效 owner | 能看到前台入口并打开预览 |
| 原型 | 未登录、非目标用户、非 active 或 owner 失效 | 不能访问预览；直接 URL 也受保护 |
| 原型 | 浏览初始 12 项及展开消息示例 | 全部为虚构数据，示例 handle 都以 `demo_` 开头 |
| 原型 | 只勾会话，不选择“我负责” | 账号仍未确认 |
| 原型 | 选择“我负责”，没有联系人或会话 | 可演示确认账号，并保留待补提示 |
| 原型 | “不是我负责”、暂缓与未处理混合 | 各状态独立，未处理项不被保存为已确认 |
| 原型 | 多联系人、一个联系人多个账号、共用群聊 | 页面可表达非一对一关系，不自动合并自然人 |
| 原型 | 只有群聊或只有私聊辅助线索 | 无强制单聊要求，不因单聊直接确认身份 |
| 原型 | 来源为 Excel、手动或相似线索 | 文案分别说明来源／线索，不显示虚构准确率 |
| 原型 | 已有其他演示负责人 | 显示冲突；不能直接“我负责”抢占 |
| 原型 | 保存后刷新当前标签页 | 合法演示状态可恢复，明确不是正式入库 |
| 原型 | 存储禁用、损坏或版本不匹配 | 可恢复初始演示并说明状态未保存；不崩溃或执行缓存内容 |
| 原型 | 重置、取消勾选、展开／关闭 | 不调用正式写接口；不改变正式数据、权限、同步或 AI |
| 原型 | 键盘及窄屏操作 | 行级动作和会话复选可分辨、可聚焦，有对应标签；状态变化可理解 |
| 正式 | 重复源行、重复导入、重复请求 | 账号和当前职责不重复；源行和幂等结果可追溯 |
| 正式 | 同账号并发确认、已有他人负责 | 最多一位当前负责人，冲突可见，不静默覆盖 |
| 正式 | 账号确认但联系人／会话为空 | 账号合法保存，关联待补不妨碍职责确认 |
| 正式 | 新会话或新来源进入已确认账号 | 只生成对应增量，不重置全量账号或自动勾选 |
| 正式 | 选择越权、失效或伪造会话 ID | 服务端拒绝关联／读取，不扩展权限，不修改 `sync_enabled` |
| 正式 | 批量部分失败、超时重试或版本变化 | 逐项结果准确；重试幂等；冲突项要求复核 |
| 正式 | 更换 handle、交接、停用或纠错 | 明确变更原因与历史，不按相似度抢占、不删除源证据 |
| 正式 | 迁移既有达人和整理台账 | 单独完成迁移预检与验收；不由原型自动转正 |

## 8. 交接与下一步

先由用户体验假数据原型，确定账号主行、负责确认、会话选择及首次／增量视图是否符合实际工作。布局和交互确认后，再单独评审正式账号模型、权限与交接流程、来源导入、事务及审计实现。

本次不建设通用流程引擎、不新增 AI 匹配服务、不承诺预览已接通真实业务。复用现有前台布局、认证和权限判定即可覆盖这轮验证。
