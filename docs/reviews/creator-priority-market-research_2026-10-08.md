# 达人重要度排行调研与技术方案

日期：2026 年 10 月 8 日。状态：第一版代码与本地验证已完成，尚未发布；发布时默认关闭，真实 API 小样本和历史初始化待完成。

建议改为**仅根据已授权聊天评估合作重要度**，不依赖 Cruva、GMV、粉丝或其他外部经营数据。AI 提取有原文依据的合作事实，Python 规则自动分档和排序；不让模型直接给一个重要度分数。

这回答的是“我们与谁已有明确合作、值得继续投入”，不是“谁的带货能力最高”。事件紧急度仍单独展示。

## 推荐方案

| 功能 | 规则 | 放在哪里 |
| --- | --- | --- |
| 合作重要度 | 重点、常规、待评估；依据来自真实合作对话 | 我的达人，增加筛选和排序 |
| 合作阶段 | 持续／再次合作、单次合作、已完成合作、具体意向 | 作为同档排序依据，不堆综合分 |
| 处理顺序 | 当前所选时段内，未处理的 P0 优先于 P1、P2；同级才参考合作重要度 | 现有消息总结，不另建待办系统 |

例如：常规达人发生付款纠纷，应先于重点达人的普通样品咨询处理。排行榜不改变身份、负责人、正文访问或发送权限。

保留 PRD v1.5 的三档分层、人工优先和重要度与紧急度分离。按本次产品方向，移除首版的外部商业指标排序及 GMV 门槛；旧 40／25／20／15 权重不用于此方案。

## 当前数据和限制

| 数据 | 当前情况 | 对方案的影响 |

聊天只能证明记录中发生或约定的事情。没读到合作、没有近期消息、附件不可读，都不等于没有合作或没有价值。现有总结的“已处理”也可能只是回答了日期，不能当作合作完成或款项到账。

## 第一版规则

### 看哪些聊天事实

| 事实 | 可接受依据 | 不算该事实的情况 |
| --- | --- | --- |
| 合作成立 | 双方明确同意具体产品、品牌、直播或视频合作 | 单方邀约、泛泛说愿意合作 |
| 持续或再次合作 | 明确长期／固定安排，或已完成合作后双方确认下一轮 | 同一次合作反复提及，不算多次合作 |
| 交付完成 | 明确说明相关内容已发布、直播已完成，并能连接到本次合作 | 寄样、承诺发布、回复“谢谢”不等于完成 |
| 实质推进 | 确认合作内容、交付安排、执行进展或下一轮合作 | 问候、催促、投诉、同群广播不自动算推进 |
| 合作机会 | 与具体产品或类目有关的明确意向和可核验经验 | 自称很有潜力、员工单方夸赞不自动升重点 |

事实须对应这位达人与公司的具体合作，保留原消息引用，并检查后续取消、改期或矛盾。群名可辅助理解背景，不能单独证明重要；第三方合作或群里其他人的成果不能算到此人身上。

### 自动分档

| 条件 | 结果 |
| --- | --- |
| 明确的持续合作正在推进，或完成合作后已确认下一轮且有有效安排 | 重点 |
| 有已成立的单次合作或明确已完成的合作，尚无持续／再次合作依据 | 常规；分别标正在推进或历史合作 |
| 首次评估且只有意向、邀约、自我介绍，或没有可靠合作事实 | 待评估，不等于低价值 |
| 已有有效事实，但新增材料不足或某项事实有冲突 | 标记受影响事实待复核，不因缺新材料覆盖仍有效的原判断 |
| 有人工设置 | 保留人工档位和依据；不同自动结论只提示复核 |

建议首轮读取近 90 天的可读聊天，用最近 30 天的实质推进或仍有效的交付安排判断近期标签和同档排序，不因超过 30 天无新消息单独降档。90／30 天是待样本验证的首版参数，不是行业标准；覆盖不足必须显示缺口。

没有新消息不推断合作终止。旧依据过期时标“需要更新依据”，不再当作新近推进；明确完结、取消或终止只更新对应合作，不推断所有合作结束。删除、撤权或身份纠错导致依据失效时立即隐藏并重算，不沿用无效依据。人工档位不自动覆盖。潜力先作为辅助标签，不凭一句积极表态升重点。

### 排序与事件

- 先按重点、常规分组，待评估单列；同档按正在推进的持续／再次合作、正在推进的单次合作、历史合作排序，再按最近一次实质推进时间和稳定人员 ID 排序。时间未知的排在同阶段已知时间之后，不用分析完成时间代替业务时间。
- 不按消息条数、群数量、@ 次数、催促次数或 AI 置信度排名；不输出 87、91 之类伪精确总分。
- 一个人多个 handle 仍是一人；同一合作在群聊、私聊或多条消息中提到，不重复加分。首版判断是否有可靠的合作事实，不统计未经去重的合作次数。
- 每位 CM 只使用本人的授权来源计算。Owner 沿用既有权限切换 CM 查看；第一版不把多份 CM 画像自动相加成公司级总分。

事件仍在消息总结中按所选时段未处理的 P0、P1、P2 排序，同级才参考合作重要度。投诉可能需要立即处理，但不提高或降低合作重要度。显示“截至该时段的进展”，不将缺总结解释成无事，不冒充跨日期的完整待办账本。

## 技术落地

### 最小存储

复用 Python、PostgreSQL、现有取材校验及持久任务模式。第一版新增三张表，审计继续使用 `audit_events`，不建立独立评分服务或向量库。

| 表 | 最小内容 |
| --- | --- |
| `creator_importance_jobs` | 达人和 CM、处理窗口、状态与租约、输入版本和指纹、分批游标、加密检查点、证据引用、重试和取材统计 |
| `creator_importance_profiles` | 达人和 CM、自动档位、合作阶段、`last_substantive_progress_at`、人工覆盖、加密的事实与依据、材料覆盖及缺口、数据截止时间、规则版本 |
| `creator_importance_requests` | 逐批请求指纹、请求及响应 ID、错误码、输入／输出 token、加密结构化返回；记录已发生的调用，即使结果后来失效也不漏记消耗 |

画像以“达人 × CM”为键，避免多负责人互相覆盖或暴露对方聊天。合作事实包含成立／计划／完成／取消／未知状态、业务对象、发生时间、引用和反证；正文与解释加密，不写入全局联系人明文字段。现有 AI 结果不能未经新协议校验直接当成合作事实。

### 更新和读取

1. 首次为正式达人按当前 CM 授权读取近 90 天记录；按日期／消息游标分批，不一次加载整个历史。保留本人和相关 CM 的发言、完整可读问答及必要上下文。
2. AI 只抽取少量合作事实和引用，不输出长理由或自行定档，不执行聊天中的指令。服务端检查引用、对象和时间，再用确定性规则生成档位及排序依据；首次无可靠事实为待评估，增量缺口不覆盖仍有效的原判断，真实反证只使受影响的事实失效并重算。
3. 新消息同步后合并短时间内的更新信号，只处理新增内容和必要上下文；按原消息 ID、业务对象和证据关联更新已有事实，不把同一交付反复加分。无明确关联的片段不能自行合并。
4. 编辑、删除、改绑、负责人解除或授权变化时，失效受影响材料并定向重算；领取、模型调用前、保存和展示均复核来源及版本。迟到结果不能覆盖新版本，撤权后立即隐藏相关结果。
5. 每日仅更新时效标记，不因过期全库调用模型。页面只查预计算画像，在分页前排序，不现场扫描聊天或调用模型。资料未同步完整时保留缺口，不把旧画像展示成实时全量结果。

名单接口沿用 `/creators`，增加等级筛选和白名单排序参数。人工调整仍限 Owner，校验当前 CM 范围、登录、CSRF、等级和依据，保存前后记录；不增加新角色或扩大正文访问。

现有七天总结可辅助召回，但不能替代 90 天事实提取，也不复用会聚合全公司授权的取材函数。第一版已将新任务接入现有 Worker、AI 配置、并发控制和用量统计，复用调度基础但保留独立任务状态。

新增独立“合作重要度”功能配置，默认关闭。历史提取会产生模型费用；以后只做增量提取、相同输入缓存复用、失败只补失败批次。分档和排序本身不调用模型，不重复全库全文分析。目前未创建 Key、调用真实 API 或启用历史评估。

可执行 Prompt、结构化协议、正反例及 Python 分档规则见[合作重要度事实提取协议 v1.0](../specs/creator-importance-facts-prompt_v1.0.md)。

### 页面和权限

在“我的达人”增加一个等级角标和“合作重要度”排序，保留负责人筛选。列表只显示“重点 · 持续合作”“常规 · 单次合作”等短标签；详情展开最多两条主要依据、数据截止时间和资料缺口。

普通 CM 只看本人范围；Owner 和已有达人管理权限按既有范围查看。仅有跨 CM 名单查看权不授予合作依据、重要度筛选或排序权限。查看排名不增加聊天权限，不因共享同一达人而共享证据。排名靠前不自动获得群发、自动回复或服务豁免。

## 验证和升级顺序

已完成本地队列、缓存、重试、来源失效、人工覆盖、权限隔离及页面布局验证；这些检查不能证明真实聊天提取的准确性。尚待完成：真实 API 小样本、90／30 天参数校验、生产发布、首次历史分析及线上增量验收。默认关闭发布不等于功能已启用。

先选少量授权完整的达人验证事实提取，再对约 200 组达人与 CM 样本做离线对照。覆盖持续、单次、历史、意向和资料不足场景；规则校准与验证使用不同样本。看重点名单的人工认可率、漏掉重要合作的比例和证据覆盖，不把模型自报置信度当准确率。

验收必须包括：意向不当作成交、寄样不当作交付、计划不当作完成、同一合作不重复计入、缺记录不降价值、人工等级不被覆盖、删除或撤权后依据失效、两个 CM 的画像不串用、常规 P0 先于重点 P2。

建议顺序是：**明确合作事实协议 → 小样本核验 → 首次历史提取与三档排行 → 新消息增量更新。** 第一版不统计精确合作次数，不建立履约订单系统或长期事件待办账本；确有需求时再升级。
