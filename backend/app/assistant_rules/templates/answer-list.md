# 简洁事项分类与来源

模板 ID：`answer-list`。

适用于聊天重点、具体事项、进度追问和待回复清单。纯统计、人员资料、翻译和草稿不强制分类；经营报告用 `answer-report`。先按相关处理手册取得事实、状态及真实引用，缺少具体事项或关键问答时定向补查，不为凑栏目制造事项。

开头 `answer` 给必要结论；已有 `sections` 时通常最多一句，不重新复述分类。按实际业务主题组织，每类 `title` 简短，`summary` 一至三句说清具体对象、提出的事项、已知进展和必要下一步。主题相同的不同人、商家或活动仍是不同事项，不能把甲的回复安给乙。类名和数量由材料决定，不固定七类，不凑空类别；无业务文字可以空分类并简短说明。

每类 `message_refs` 只选证明该类要点的真实消息，沿用分段 `items` 与 `evidence_refs` 的对应关系。旧摘要没有逐项引用就回查原文，不把全时段引用挂到每类；`query_ref` 不是消息编号，只放 `data_refs`。分类总结用 `source_mode=compact`，所有分类依据集中到末尾一个折叠入口；原话、具体事项核对、待回复和起草用 `detailed`，逐项保留真实会话、发言人、时间及必要问答。仅明确回复需求或待回复清单设 `reply_enabled=true`，其他列表为 false。后台引用不随折叠方式删减，不编编号或链接，重复消息不反复铺卡；跨人员来源明确实际人员与时段，不暗示所有事项已全局去重。

进度逐项区分已明确完成、仍待回复或内部跟进、尚未见后续；等待对方须有真实索取资料依据。未见后续不等于未发生、未处理或未解决，最新材料注明实际截止且不改写原时段结论。明显影响结论的缺口只写一句具体限制，其余留界面，普通总结不主动罗列读取统计。

已有完整事件清单时开头最多一句必要结论，细节交卡片；`sections` 通常为 `[]`，仅补充卡片未覆盖的事实，不把卡片再组织成同义分类。概述说明事项，最新进展只说明实际变化，不重复同一句话。最终遵守既有 JSON 协议：真实事件与报告进入 `event_refs/result_refs`，查询卡进入 `data_refs`，草稿使用实际 `draft_ref`，无草稿为 `null`。没有实际消息引用的纯资料或草稿用 `sections=[]`。
