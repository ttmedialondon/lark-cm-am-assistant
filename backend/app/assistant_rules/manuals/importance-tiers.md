# 达人维护分档与人工调整说明

## 用途与边界

本手册说明现有系统如何分档，供后台编辑者理解结果，不参与模型事实提取。修改本文不会改变代码中的时间窗口、排序、权限或人工优先机制；调整这些产品规则需要修改并验证程序，不能只改文档。

维护优先级回答“这位 CM 当前应优先维护谁”，不是达人价值评级，也不是事项的 P0–P3 紧急度。同一达人在不同 CM 下分别评估，仅使用该 CM 当前可读的记录；多负责人不共享聊天依据。Curva、GMV、粉丝量和模型置信度不参与分档，不新增综合分。

## 现有五档

先采用有效人工档位；没有人工调整时，自动档位按下表从上到下判断。

| 档位 | 现有条件 |
| --- | --- |
| 重点 | 近 7×24 小时有仍有效的具体机会、单次／持续交付安排或实质推进；后续完成、取消或真实冲突已关闭的对象不算。可靠的一项即可，不设消息数量门槛。 |
| 优先 | 上述主要事项已超过 7 天但仍在近 30×24 小时内；或近 30 个英国自然日期内，至少 3 个不同日期有有效双边业务交流。频率只能升至优先，不能证明合作成立。 |
| 久未联系 | 未满足重点／优先，当前画像及来源有效，且当前记录中最近相关消息已超过 30×24 小时。不是因为查不到消息就判沉默。 |
| 常规 | 已有有效可读正文，未满足上述条件。单向意向、问候和旧合作本身不升档；完成合作后仍可因独立的近期业务交流达到优先。 |
| 待评估 | 尚未评估完、来源失效，或没有足够可读资料且无已知旧消息支持久未联系。表示资料不足，不表示达人不重要。 |

分档判断顺序与列表排序不同：列表仍为“重点 → 优先 → 常规 → 久未联系 → 待评估”。同档沿用现有时效带、英国业务日期数、最近推进时间、历史合作背景及稳定姓名／人员 ID 排序，不累加消息、群或 handle 分数。

## 时间和依据

- 7／30 天主要事项窗口按原消息时间滚动，不按模型运行日期计时。近 30 个业务日期按 `Europe/London` 的今天及之前 29 个自然日期去重，重复消息不多算一天。
- 有效日期来自双方受控引用；双边意向、具体业务交流和合作事实均可形成日期，单向广播、问候和纯催款不算。
- 每个具体合作独立推进状态。完成、取消和真实冲突关闭其主要依据；另一合作继续保留。没有新事实不会清空旧事实。
- 久未联系所用最近消息来自当前 CM 可读范围内的达人本人发言（含媒体）、CM 发给该达人的私聊，或仍有效的受控引用；无关群广播不刷新联系时间。已删除、未来或其他 CM 的消息不计。
- 档位可以随天数变化，不必为过期重新调用模型。旧机会超过 30 天不再维持重点／优先，历史合作也不永久压过新机会；是否久未联系仍看真实已知最近消息。
- 来源删除、编辑、撤权或身份变化时，自动结果先受当前来源校验约束，受影响资料由现有队列更新；没有资料不能宣称现实中完全没联系。页面保留简洁档位，不要求展示全部事实或新增解释卡片。

## 人工调整

沿用现有 Owner 调整权限，对“达人 × CM”分别保存档位和简短理由。人工档位优先于自动结果；后台更新、手册编辑和时间流逝不覆盖人工设置。清除人工调整后，恢复当前有效自动结果；自动材料尚不可用时显示待评估。

本次接入不改已有人工值、正式达人及负责人关系，不全量重跑，不更改功能开关或模型配置。后续正常新增、增量和定向更新继续使用原队列；发布手册不是全库重新评估的指令。
