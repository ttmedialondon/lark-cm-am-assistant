# 人员与账号关联规则

对每个精确 TikTok handle 独立判断与目标联系人的关系。身份成立不意味着本人提及的所有账号都属于自己。

## 账号来源

允许精确合作群主名、明确 TikTok 主页链接、带账号语境的本人填报或业务问答，以及 Curva 辅助目录。保留点、下划线和数字，只规范化大小写、合法前缀与主页路径；不靠近似拼写自动纠错。

Curva 未收录不否决明确账号；已确认 Excel 或人工关系也不因此清理。普通正文词语、商品链接参数、邮箱前缀或仅相似姓名不能直接成为正式账号。

## 四类本人关联证据

| 依据 | 要求 |
| --- | --- |
| 本人声明 `self_claim` | 有明确 TikTok 语境的自述，如 “My handle is X” 或 “I'm Daisy from X on TikTok” |
| 自然问答 `qa_confirm` | 真实问题或业务填报明确指向本人账号；本人按回复链或连续对话给出账号，不限固定问句 |
| 本人主页 `own_page` | 本人说明“我的主页”等，并给出精确主页；单独转发链接不成立 |
| 群名联合 `group_context` | 固定合作群主名精确包含该账号，同时该群本人真实发言涉及自己的账号、创作或直播履约；群名是强关联证据，不能脱离本人业务独立确认 |

对未确认人员，还须依据达人身份证据规则独立证明身份。不得把现行 `creator_known=true` 下的宽松账号补配，直接当作新人员身份已确认。

## 必须分开的关系

本人账号、本人作品所在账号、替他人运营、他人账号、仅提及、关系未知分别记录。作品出现在某账号、处理账号问题或认识账号主人，都不必然是本人账号。

一个人多个账号逐项返回；一个弱候选不影响另一强候选。群名括号中的备用账号不继承主号结论。改名、备用号、旧号、已删除账号和转让分开处理；消息时点的自述不能冒充平台当前控制权验证。

当前正式数据库只允许一个 handle 对应一位 `owner` 联系人，支持一人多 handle、多 CM。发现多人指向同号进入冲突复核，不自动合并人员或抢占关系；共用账号与同一自然人的多个 Lark 身份另行定义，不能靠提示词绕过约束。

## 复用与提交

同一人已经正式关联的精确账号默认跳过，只判断其新账号。仅主动复核或数据库已查实的身份、归属冲突重查旧关系；不因一次弱模型结果撤销现有关系。

沿用当前 v1.11 输出协议：逐账号 `supported/review/not_supported`，并记录 `relation/period/code/refs/needed`。正式新增本人关联要求 `supported + self_account + at_message + 上述四类证据 + needed=[]`，再通过当前授权、引用、版本与冲突校验。这个协议没有匹配百分比门槛。

证据不足、回复链不完整、明确旧账号、改名或转让关系、具体归属冲突进入待核实；不能仅因消息较旧否定 `at_message` 的关联。合法候选中的错误引用只影响该候选，不能让整批有效账号失败。

现行执行 prompt 在 `docs/specs/creator-handle-association-prompt_v1.2.md` 中，实际协议版本已为 v1.11；本手册尚未替代该文件。
